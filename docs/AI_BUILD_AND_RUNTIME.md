# Сборка и выполнение E3D Editor

Обновлено: 2026-10-20 01:16 UTC+3.

Документ является единственным подробным справочником по подготовке, сборке,
публикации и выполнению приложения. Практические инструкции находятся
в [HTML-руководстве](user-guide/index.html), архитектурные границы — в
[`AI_ARCHITECTURAL_RULES.md`](AI_ARCHITECTURAL_RULES.md), поведение интеграции
с установленным Clark — в [`AI_CLARK_INTEGRATION.md`](AI_CLARK_INTEGRATION.md).

## Термины

- **режим разработки** — выполнение исходного кода через Vite dev server;
- **production-сборка** — создание оптимизированного статического комплекта
  файлов в `dist`;
- **preview** — локальная проверка уже созданного `dist` через Vite;
- **развёртывание** — публикация `dist` через постоянный HTTP/HTTPS-сервер.

Production-сборка сама приложение не запускает. Сначала создаётся `dist`, после
чего его содержимое должно раздаваться сервером.

## Команды

| Команда                 | Назначение                                            |
|-------------------------|-------------------------------------------------------|
| `npm run dev`           | Подготовить ресурсы и запустить dev server            |
| `npm run build`         | Создать и проверить production-сборку в `dist`        |
| `npm run build:release` | Явно создать сборку в режиме `production`             |
| `npm run build:pages`   | Создать сборку с базовым путём `/clark-editor/`            |
| `npm run preview`       | Локально показать уже созданный `dist`                |
| `npm test`              | При необходимости запустить тесты без браузера       |

Обычная команда `vite build` по умолчанию использует режим `production`.
Поэтому `npm run build` и `npm run build:release` в текущей конфигурации дают
практически одинаковый результат. Вторая команда явно фиксирует назначение
сборки и используется release-сценариями.

## Время сборки

`npm run build`, `build:release` и `build:pages` вызывают `scripts/build.mjs`.
Он последовательно запускает прежние инструменты подготовки библиотек,
примеров, демозадания и HTML-руководства, Vite с соответствующими аргументами, затем проверку
SHA-256. Дочерние процессы используют текущий Node.js и корень проекта;
вызов не зависит от текущего каталога и не требует shell-команд для Vite.
При изменении состава подготовки ресурсов необходимо синхронно обновлять
`assets:prepare` и список этапов в `scripts/build.mjs`.

Последняя строка — `Время сборки [build:release]: 0.06 мин.`: весь интервал
подготовки, Vite и проверки ресурсов, а не только время внутри Vite.
Монотонный `performance.now()` исключает влияние системной даты; минуты
выводятся с двумя десятичными знаками. При ошибке этапа следующие этапы
не запускаются, его ненулевой код передаётся npm и итог времени сохраняется.
Дополнительные аргументы npm после `--` передаются Vite.

`scripts/build-local.cmd` дополнительно показывает общий интервал с `npm ci`;
`scripts/release-lan.cmd` — весь интервал выпуска, включая настройку/запуск
Caddy. Вложенные итоги различаются именами команд. CMD использует монотонный
помощник `scripts/Write-BuildTime.ps1`, штатный Windows PowerShell и выводит
итог перед интерактивной паузой. Сохранённые коды завершения не меняются.
Принудительное уничтожение процесса не гарантирует завершающий вывод.

## Режим разработки

Команда

~~~bat
npm run dev
~~~

сначала выполняет `assets:prepare`, затем запускает Vite dev server. Подготовленные
файлы базовых библиотек размещаются в `.generated/data/default`; Vite использует
`.generated` как `publicDir` и раздаёт эти файлы вместе с приложением.
В ту же подготовку входят настройки и файлы примеров, комплект демозадания
`.generated/demo-task.json` и `user-guide`.

В этом режиме:

- итоговый комплект `dist` не создаётся и не обновляется;
- исходные ES-модули преобразуются по запросу браузера;
- изменения кода обычно применяются через Hot Module Replacement без полной
  перезагрузки страницы;
- Vite показывает подробную диагностическую панель и удобные стеки ошибок;
- скорость загрузки и состав сетевых запросов не характеризуют релизную сборку.

На Windows команда `scripts/dev.cmd` при отсутствии `node_modules` предварительно
выполняет `npm ci`, запускает dev server и открывает браузер.

## Production-сборка

Команда

~~~bat
npm run build:release
~~~

выполняет следующую последовательность:

1. `assets:prepare` формирует базовые библиотеки в `.generated`, копирует
   настройки и дерево примеров, создаёт список файлов для их установки,
   затем формирует комплект демозадания `demo-task.json`.
2. Vite обрабатывает достижимый граф модулей и создаёт `dist`.
3. JavaScript и CSS оптимизируются, а имена ресурсов получают хеши для
   безопасного кеширования.
4. Содержимое `publicDir` копируется в `dist`.
5. `assets:verify` сверяет комплект `dist/data/default` по SHA-256.

Исходные карты для production-сборки в `vite.config.js` не включены. Поэтому
стек ошибки в релизе может быть менее наглядным, чем в режиме разработки.

Команды `build` и `build:release` не запускают `npm test`. Локальная сборка
на Windows с чистой установкой зависимостей выполняется сценарием:

~~~bat
scripts/build-local.cmd
~~~

Он последовательно выполняет `npm ci` и `npm run build:release`.

Тесты запускаются отдельно, когда они помогают проверить рискованное изменение
или конкретную проблему. Обязательного прогона при каждой правке, сборке или
публикации нет. Workflow `Build editor` автоматически собирает
редактор на Linux и Windows; при ручном запуске `workflow_dispatch` можно включить
параметр `run_tests` для выполнения тестов перед сборкой на обеих системах.
По умолчанию он выключен. Workflow публикации GitHub Pages выполняет сборку и
публикацию без запуска тестового набора. Проверка ресурсов `assets:verify`
остаётся частью сборки.

## Выполнение готовой сборки

Для локальной проверки `dist`, созданного командой `build` или
`build:release`, используется:

~~~bat
npm run preview
~~~

После `build:pages` используйте `npm run preview -- --base=/clark-editor/`.
Полная последовательность приведена в разделе публикации ниже.

Vite preview предназначен для проверки результата сборки, а не для постоянного
развёртывания приложения.

Для работы в локальной сети предусмотрен:

~~~bat
scripts/release-lan.cmd
~~~

Сценарий создаёт локальную release-сборку и запускает Caddy. Конфигурация
`deploy/caddy/Caddyfile`:

- раздаёт содержимое `dist` по HTTPS;
- включает сжатие Zstandard и gzip;
- отдельно обслуживает `/data/default/*`;
- для остальных неизвестных маршрутов возвращает `index.html`, обеспечивая
  работу SPA после обновления страницы.

Открывать `dist/index.html` непосредственно через `file://` не следует: пути
ресурсов, маршрутизация SPA и браузерные разрешения рассчитаны на HTTP/HTTPS.

## Фактические различия при выполнении

| Свойство    | Разработка                  | Релиз                                |
|-------------|-----------------------------|--------------------------------------|
| Источник    | Модули из `src`             | Оптимизированные файлы из `dist`     |
| Обновление  | HMR после изменения файла   | Новая сборка и обновление страницы   |
| Диагностика | Подробная, по исходникам    | Стек минифицированных файлов         |
| Кеширование | Ориентировано на разработку | Хешированные ресурсы                 |
| Сервер      | Vite dev server             | Preview, Caddy или сервер публикации |

В приложении нет отдельных ветвей прикладной логики для
`import.meta.env.DEV`, `PROD` или `MODE`. Форматы заданий, валидация и поведение
редактора должны совпадать в обоих режимах.

Используется `import.meta.env.BASE_URL`: через него формируются адреса базовых
библиотек. Обычная и LAN-сборки работают от корня `/`, а `build:pages` задаёт
путь `/clark-editor/`. Ошибка при выборе варианта сборки обычно проявляется как
отсутствие статических ресурсов после публикации.

## Браузер и безопасный контекст

Доступ к локальному каталогу задания основан на File System Access API.
Полная функциональность редактора гарантируется для браузеров Google Chrome
или Microsoft Edge. Выбор этих браузеров рекомендуется; ограничения по названию
браузера нет. Перед файловым диалогом редактор проверяет необходимые методы API
и безопасный контекст:

- `localhost` при `npm run dev` или `npm run preview` считается безопасным;
- LAN-релиз использует HTTPS через Caddy; корневой сертификат Caddy должен быть
  установлен на клиентском компьютере как доверенный;
- адрес вида `http://<LAN-IP>` может открыть интерфейс, но не предоставить
  операции чтения и записи локального каталога.

После запуска сервера публичный корневой сертификат находится в
`deploy/caddy/root.crt`. На каждом клиентском компьютере его устанавливают с
проверкой показанного сервером SHA-256:

~~~bat
scripts/caddy/install-root-ca.cmd "<путь-к-root.crt>" <SHA-256>
~~~

Эти ограничения относятся к среде выполнения браузера, а не к способу сборки
JavaScript.

## Выбор сценария

- ежедневная разработка интерфейса: `npm run dev`;
- тесты при необходимости: `npm test`;
- локальная release-сборка: `scripts/build-local.cmd`;
- запуск релиза в локальной сети: `scripts/release-lan.cmd`;
- публикация GitHub Pages: `npm run build:pages` через GitHub Actions.

## Публикация релиза на GitHub Pages

Регламент предназначен для самостоятельного выпуска редактора без участия ИИ.
Он описывает уже работающую схему: исходники из `main` собираются на GitHub,
а результат публикуется как статический HTTPS-сайт. Каждая публикация связана
с конкретным Git-коммитом и запуском Actions. Создание тега или записи
в разделе GitHub Releases этой схемой не предусмотрено и для выпуска не нужно.

### 1. Предварительные условия

Используются репозиторий
[y26084670-blip/web-gui](https://github.com/y26084670-blip/web-gui), ветка
`main` и существующий workflow
[deploy-pages.yml](../.github/workflows/deploy-pages.yml) с названием
`Build and deploy GitHub Pages`.

Для отправки изменений и ручного запуска workflow нужен доступ на запись
в репозиторий. GitHub Desktop должен быть подключён к этому репозиторию.
Локальная проверка требует Node.js 24 с npm; для сборки на стороне GitHub
локальная установка Node.js не требуется.

В уже настроенном проекте настройки Pages при каждом выпуске не меняются.
При восстановлении настройки откройте `Settings → Pages` и убедитесь, что
в `Build and deployment → Source` выбран `GitHub Actions`.
Используйте имеющийся workflow. Порядок выбора источника описан в
[GitHub Docs](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

Адрес сайта берите из `Settings → Pages → Visit site` либо из ссылки окружения
`github-pages` в успешном запуске. Сборка проекта настроена на базовый путь
`/clark-editor/`; изменение адресной схемы требует отдельной корректировки сборки.

### 2. Подготовка исходников

1. В GitHub Desktop выберите репозиторий `web-gui` и `Current branch: main`.
   Нажмите `Fetch origin`, затем `Pull origin`, если доступны входящие
   изменения. Согласуйте их с текущими локальными правками до проверки сборки.
2. Подготовьте изменения к выпуску. Список `Changes` должен содержать только
   предназначенные для публикации файлы. Перед отправкой ещё раз просмотрите
   их содержимое и выбранные флажки.
3. Если изменены примеры, включите их исходное дерево
   `public/examples/clark.projects`; если изменены настройки загрузок —
   `public/examples-config.json`. Подготовка этих материалов описана в
   [отдельном разделе](#примеры-и-установщик-решателя).
   Для изменения демонстрационного задания включите исходные файлы `data/demo`;
   подготовка комплекта описана в разделе [«Демонстрационное задание»](#демонстрационное-задание).
4. Обновите minor или patch по [правилам версионирования](AI_IMPLEMENTATION_PROTOCOL.md#4-версионирование),
   согласованно изменив `package.json` и корневые записи `package-lock.json`.
5. По необходимости проверьте изменённый сценарий. Локальная контрольная
   сборка и запуск `npm test` выбираются по риску правки согласно
   [`AI_VERIFICATION.md`](AI_VERIFICATION.md); обязательного прогона каждого
   вида проверки при каждом выпуске нет.

GitHub собирает только отправленное содержимое репозитория. Незакоммиченные
файлы и материалы, существующие лишь на локальном диске, в публикацию не входят.
`node_modules`, `.generated` и `dist` исключены через `.gitignore`:
их создаёт сборка, добавлять их в коммит вручную не требуется.

Ручная правка локального `dist/examples-config.json` подходит для отдельно
размещаемого комплекта, но не переносится в автоматический выпуск Pages.
Для Pages изменяйте исходный `public/examples-config.json` и отправляйте
его в репозиторий.

Команды сборки и workflow не увеличивают номер версии автоматически.
Повышение версии включайте в подготовку выпуска, а не откладывайте до
публикации. Текущий выпуск — **4.20.3**. Повторная публикация того же состояния
без изменений не требует нового номера. Для точного определения опубликованного
состояния дополнительно используйте SHA коммита в Actions.

### 3. Локальная контрольная сборка

Раздел описывает доступный локальный сценарий; он выполняется по необходимости
и не является условием каждого выпуска. Автоматическая сборка на GitHub
остаётся штатной частью публикации. Для выпуска 4.20.3 локальная сборка,
тесты и дополнительные проверки, включая браузерные, не запускались по
указанию пользователя. Обновление `main` использует обычный workflow без
дополнительного запуска проверок или контроля результата публикации.

Этот этап позволяет проверить готовое приложение до отправки изменений.
Команды выполняйте в PowerShell из корня локального репозитория по одной;
при ошибке остановитесь и исправьте её до следующего шага.

~~~powershell
cd D:\JOB_LV\clark.gui
node --version
npm --version
npm ci
npm run build:pages
npm run preview -- --base=/clark-editor/
~~~

`node --version` должен показать `v24.x.x`. `npm ci` устанавливает
зависимости по `package-lock.json`. Команда `build:pages` создаёт `dist`
с тем же базовым путём, который используется в Actions.
После успешной сборки последняя команда запускает локальный сервер.
При текущей конфигурации откройте
[локальную Pages-сборку](http://127.0.0.1:4173/clark-editor/) в Chrome или Edge.
Держите PowerShell открытым; для остановки сервера нажмите `Ctrl+C`.

Для обычной release-сборки, обслуживаемой от корня сайта, после `npm ci`
используются другие две команды:

~~~powershell
npm run build:release
npm run preview
~~~

В этом случае адрес — [локальная release-сборка](http://127.0.0.1:4173/).
Windows-сценарий `scripts\build-local.cmd` выполняет `npm ci` и
`build:release`; просмотр запускается отдельно.

Оба варианта записывают результат в один каталог `dist`: последняя сборка
заменяет предыдущую. При смене варианта остановите preview, соберите нужный
вариант и запустите preview с соответствующим `base`. Значение `base`,
переданное при сборке через командную строку, не сохраняется в
`vite.config.js`, поэтому для Pages оно явно передаётся и при просмотре.
Опция предусмотрена [Vite CLI](https://vite.dev/guide/cli.html#vite-preview).

Локальная сборка ничего не отправляет на GitHub. Она проверяет приложение
в локальном окружении; успешная публикация на сервере подтверждается отдельно.

### 4. Фиксация и отправка изменений

1. В GitHub Desktop откройте `Changes`, проверьте выбранные файлы и заполните
   `Summary` кратким описанием выпуска.
2. Нажмите `Commit to main`. Коммит сохраняется локально.
3. Нажмите `Push origin`. После успешной отправки этот коммит появится
   в `main` на GitHub и автоматически запустит публикацию.
4. Перейдите на
   [страницу публикующего workflow](https://github.com/y26084670-blip/clark-editor/actions/workflows/deploy-pages.yml).
   Найдите запуск по сообщению или SHA только что отправленного коммита.

Если `Push origin` отклонён из-за новых удалённых изменений, получите их,
разрешите возможные конфликты и проверьте итоговую версию перед новой отправкой.
Если нужный коммит уже отправлен, переходите сразу к проверке его запуска
или ручной повторной публикации; создавать дополнительный коммит не нужно.

Текущий workflow реагирует на каждый обычный `push` в `main`, включая правки
только Markdown: фильтра по путям файлов в нём нет. Поэтому отправка в
`main` одновременно является действием выпуска. Отдельная команда
«Опубликовать релиз» после `Push origin` не требуется.

### 5. Что выполняет GitHub

Workflow содержит одно задание `deploy`, выполняемое на `ubuntu-latest`
только для `refs/heads/main`. Предельное время задания — 15 минут.

| Шаг в журнале Actions | Действие и результат |
|---|---|
| `Check out the repository` | Получение исходников коммита данного запуска |
| `Set up Node.js` | Подготовка Node.js 24 и кеша npm |
| `Install dependencies` | `npm ci`: установка зависимостей по lock-файлу |
| `Build the GitHub Pages bundle` | `npm run build:pages`: подготовка ресурсов, production-сборка с `--base=/clark-editor/`, проверка базовых библиотек |
| `Configure GitHub Pages` | Подготовка параметров Pages |
| `Upload the Pages artifact` | Передача содержимого `./dist` как артефакта публикации |
| `Deploy to GitHub Pages` | Развёртывание артефакта и формирование ссылки на сайт |

Исполняемые команды определены в [package.json](../package.json), а порядок
и разрешения — в [deploy-pages.yml](../.github/workflows/deploy-pages.yml).
Подробности внутренней сборки описаны в разделе «Production-сборка».
Публикация завершается только после шага `Deploy to GitHub Pages`;
загрузка артефакта сама по себе ещё не означает обновления страницы.

В Actions могут одновременно отображаться другие workflow, в частности
`Build editor`. Для подтверждения публикации нужен
именно успешный `Build and deploy GitHub Pages`.

Группа `concurrency: github-pages` с `cancel-in-progress: true` отменяет
предыдущий выполняющийся запуск этой группы при новом запуске. Если быстро
отправлены несколько коммитов, проверяйте результат самого нового нужного
коммита. Отменённый предыдущий запуск в таком случае не означает ошибку сборки.
Это следует из конфигурации проекта и
[правил workflow GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

### 6. Проверка опубликованной страницы

1. Откройте нужный запуск и убедитесь, что `deploy` завершён со статусом
   `Success`, а последний шаг публикации выполнен. Сверьте SHA коммита.
2. Откройте ссылку сайта из окружения `github-pages` либо через
   `Settings → Pages → Visit site`. Используйте HTTPS;
   в качестве браузера рекомендуются Chrome или Edge.
3. Обновите страницу. Если видна прежняя версия, выполните `Ctrl+F5`.
4. Проверьте именно изменённый сценарий. При изменении загрузки данных
   выберите локальный базовый каталог, проект и задание; при изменении
   геометрии или таблиц проверьте их отображение. Проверку сохранения
   выполняйте на отдельном проверочном задании.
5. Если выпуск менял примеры, проверьте «Установить примеры» и открытие
   полученного задания. Если менялась ссылка установщика, проверьте открытие
   облачного каталога. Пустой `solverInstallerUrl` означает штатную недоступность
   установщика и не свидетельствует о сбое публикации редактора.

Зелёный статус подтверждает предусмотренные workflow сборку, проверку ресурсов
и публикацию. Он не подтверждает работу всех функций интерфейса:
браузерный сценарий проверяется отдельно, а `npm test` данный workflow
не запускает. После завершения Actions следует дождаться обновления страницы
на стороне Pages и повторить загрузку, если изменение ещё не видно.

### 7. Повторная публикация без новых изменений

Чтобы заново собрать и опубликовать актуальный `main`:

1. Откройте `Actions → Build and deploy GitHub Pages`.
2. Нажмите `Run workflow`.
3. В выборе ветки укажите `main`.
4. Нажмите подтверждающую кнопку `Run workflow`.
5. Откройте появившийся запуск и выполните проверку результата из раздела выше.

Ручной запуск разрешён существующим `workflow_dispatch`. При выборе другой
ветки задание `deploy` будет пропущено из-за условия в workflow.
Если кнопки нет, проверьте, что открыта страница самого workflow, файл присутствует
в основной ветке и у учётной записи есть права на запись. См.
[ручной запуск в GitHub Docs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

`Re-run jobs` / `Re-run all jobs` на странице прежнего запуска повторяет
его исходный коммит и ref. Эта команда подходит для повторения временно
неудавшегося запуска того же коммита. Для текущего состояния `main`
используйте новый `Run workflow`.
[Правила повторного выполнения](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)
объясняют сохранение исходных `GITHUB_SHA` и `GITHUB_REF`.

### 8. Диагностика и восстановление

При красном статусе откройте запуск, задание `deploy` и первый неуспешный
шаг. Исправлять следует указанную в его журнале причину.

| Признак | Что проверить и как продолжить |
|---|---|
| Запуска нет после локального коммита | Выполнен ли `Push origin`, присутствует ли коммит именно в `main` на GitHub |
| `deploy` имеет статус `Skipped` | Выбрана ли ветка `main` при ручном запуске |
| `Cancelled` у прежнего запуска | Есть ли более новый запуск той же публикации; дождаться его результата |
| Ошибка `Install dependencies` | Журнал `npm ci`, согласованность `package.json` и `package-lock.json`, доступность реестра пакетов; после исправления повторить локальную установку |
| Ошибка сборки или `assets:verify` | Первый текст ошибки, наличие исходных ресурсов; воспроизвести через `npm ci` и `npm run build:pages` |
| Сборка успешна, публикация неуспешна | Журналы `Configure GitHub Pages` и `Deploy to GitHub Pages`, источник Pages и разрешения окружения `github-pages` |
| Пустая страница или ресурсы возвращают 404 | Адрес сайта, путь `/clark-editor/`, использование `build:pages` и артефакта `dist` |
| Видна прежняя версия | SHA последнего успешного Pages-запуска, завершение публикации, обновление `Ctrl+F5` |
| Нельзя выбрать локальный каталог | Наличие нужных методов File System Access API, HTTPS, разрешение на выбранный каталог; рекомендуются Chrome или Edge |
| Примеры отсутствуют или старые | Отправлено ли исходное дерево `public/examples/clark.projects`; локальные правки `dist` в Actions не используются |

При временной ошибке сервиса или сети можно повторить запуск. При ошибке
исходников сначала исправьте причину и отправьте новый коммит; повтор той же
сборки с теми же исходниками проблему не устраняет.

Если опубликованная версия содержит регрессию, восстановите нужное состояние
новым отменяющим коммитом:

1. В GitHub Desktop получите актуальный `main`, откройте `History`
   и найдите коммит, который внёс неудачное изменение.
2. Откройте его контекстное меню и выберите `Revert Changes in Commit`.
   Выбирается именно неудачный коммит: команда отменяет изменения выбранного
   коммита, а не устанавливает его состояние как целевую версию.
3. Проверьте результат отмены. Для нескольких коммитов двигайтесь от более
   новых к старым; при конфликтах сначала разрешите их. Учитывайте, что отмена
   коммита затрагивает все внесённые им изменения.
4. Выполните нужную локальную проверку и `Push origin`. Новый коммит в
   `main` запустит обычную сборку и публикацию.
5. Проверьте успешное завершение нового запуска и восстановленный сценарий
   на сайте.

Такой откат сохраняет историю и делает восстановленное состояние исходников
основой дальнейших выпусков. См.
[отмену коммита в GitHub Desktop](https://docs.github.com/en/desktop/managing-commits/reverting-a-commit-in-github-desktop).
Повтор старого запуска Actions не изменяет состояние `main` и не заменяет
этот порядок восстановления исходников.

## Типичные расхождения режимов

- Изменение видно в dev server, но отсутствует в релизе: `dist` не пересобран
  либо браузер использует старый документ из кеша.
- Статические файлы возвращают 404: сборка создана с неверным `base` или сервер
  публикует не тот каталог.
- После обновления вложенного адреса возвращается 404: сервер не настроен на
  SPA fallback к `index.html`.
- Выбор каталога недоступен: отсутствуют необходимые методы File System Access
  API, разрешение на каталог либо безопасный контекст.
- Ошибка появляется только при сборке: production-сборщик обрабатывает весь
  достижимый граф модулей, тогда как dev server мог ещё не запросить проблемный
  модуль.

## Сводка результатов расчёта

На вкладке «Выбор задания» три панели подписаны снизу по центру:
«выбор задания», «исходные данные», «результаты». Подписи находятся вне
прокручиваемого содержимого. Правая панель без верхнего заголовка читает
`<выбранное задание>/output3XX/_summary_out.txt`. Это обычный текстовый файл
UTF-8, отображаемый без разбора формата, с сохранением пробелов и переводов
строк. Окно занимает доступную высоту над подписью и позволяет выделять, копировать и
прокручивать текст; редактирование содержимого отключено.

Файл читается при выборе задания и повторном щелчке по тому же заданию.
Поэтому после расчёта достаточно снова выбрать его строку. При отсутствии
файла отображается точное сообщение «нет данных по результатам или расчет не
проводился». Чтение использует локальный каталог, уже выбранный пользователем.
Редактор не создаёт сводку результатов. Запуск расчёта передаётся локальному
Clark через отдельное окно списка заданий.

Сводка исходных данных в средней панели продолжает загружаться из
`input3XX/_summary.txt`; она имеет отдельное назначение и формат.

## Запуск локального Clark из редактора

Начиная с 4.20.0 под «Загрузить для редактирования» доступна кнопка
«Формирование списка заданий и запуск приложений». Она открывает плавающее окно управления файлом
`clark.tasks.txt` в корне выбранного базового каталога. Пользовательский
сценарий описан в [README](../README.md#список-заданий-и-запуск-clark),
точный контракт списка и протокола — в `AI_CLARK_INTEGRATION.md`.

Кнопка «Выбрать каталог с проектами» допускает произвольное имя базового
каталога; `clark.projects` остаётся обычным именем каталога примеров.

Браузер продолжает читать и записывать файлы через File System Access API.
Windows-обработчик `clark://`, устанавливаемый вместе с Clark, связывает
идентификатор базового каталога с его абсолютным путём и создаёт из корневого
TXT временный снимок с абсолютными путями для штатных команд расчёта, клиента
цепи и импорта. Постоянно работающий
локальный HTTP-сервер не требуется. Размещение редактора на GitHub Pages,
Caddy или другом HTTPS-сервере не меняет эту схему.

Выпуск состоит из двух независимо доставляемых частей:

1. Обновление `web-gui/main` запускает обычный workflow сборки и публикации
   страницы. Оно доставляет только редактор и его статические ресурсы.
2. Исходники поставки Clark обновлены до 0.10.0. Штатная следующая сборка
   установщика повышает patch до 0.10.1; полученный комплект нужно отдельно
   опубликовать и установить на компьютере пользователя. Именно установка
   регистрирует обработчик `clark://`. Уже установленный прежний Clark
   автоматически от публикации страницы не обновляется.

После обновления Clark пользователь один раз нажимает «Связать с Clark»,
после подготовки списка, перед первым запуском для выбранного каталога,
подтверждает открытие программы браузером и выбирает в системном диалоге
тот же базовый каталог. Диалог поясняет требуемый выбор и показывает
фактическое имя папки. После переноса или копирования каталога связывание
нужно повторить для нового расположения. Встроенная Демо не использует
локальный запускатель.

В этом цикле подготовлены исходники обеих частей; бинарный установщик,
локальная контрольная сборка редактора, тесты и браузерные проверки не
выполнялись. Для проверки сценария в реальной работе требуется установленная
поставка с новым обработчиком. Успешная публикация Pages сама по себе не
подтверждает наличие этого обработчика на компьютере пользователя.

## Демонстрационное задание

Исходные данные хранятся в `data/demo`: текущий комплект содержит семь файлов
непосредственно в корне каталога. Скрипт `scripts/prepare-demo-assets.mjs`
выполняется последним в `assets:prepare`, после подготовки базовых библиотек
и примеров. Он создаёт `.generated/demo-task.json` с относительными путями
и содержимым файлов в Base64. Такое представление сохраняет исходные байты
при доставке одним статическим ресурсом.

Vite раздаёт комплект из `.generated` в режиме разработки и копирует его
в `dist` при сборке. Загрузчик учитывает `import.meta.env.BASE_URL`, включая
`/clark-editor/` для GitHub Pages. Действующий workflow публикации использует
ту же подготовку ресурсов; отдельного этапа или настройки сервера не требуется.
После изменения `data/demo` повторите подготовку ресурсов либо обычную команду
разработки или сборки, чтобы обновить комплект.

Кнопка «Демо» загружает комплект без File System Access API и представляет
его файлы как содержимое `input3XX` демонстрационного задания. Рабочая копия
в памяти поддерживает чтение и запись для обычных редакторов и операций
с локальными характеристиками. Общая кнопка «Сохранить модель» отключена;
изменения не записываются в опубликованный комплект. Повторная загрузка
демо создаёт копию исходных данных заново, а перезагрузка страницы удаляет
рабочую копию. Замена загруженной модели сохраняет обычное предупреждение
о несохранённых изменениях. При переходе к локальному заданию действует
обычный сценарий сохранения.

## Примеры и установщик решателя

Примеры хранятся на сервере обычными файлами. Исходное дерево для сборки —
`public/examples/clark.projects`: внутри находятся проекты, затем задания со
всеми нужными legacy-файлами, `input3XX` и результатами расчёта. Копируются все
расширения и пустые каталоги. Содержание заданий не разбирается и не изменяется.

Ссылки задаются в `public/examples-config.json`:

~~~json
{
  "manifestUrl": "examples-manifest.json",
  "solverInstallerUrl": "https://cloud.mail.ru/public/nLj8/CVS8JAToQ"
}
~~~

`manifestUrl` указывает служебный список файлов. `solverInstallerUrl` содержит
ссылку на публичный облачный каталог с актуальной версией установщика решателя.
Адреса в панели не показываются и пользователем не редактируются. Они доступны
браузеру как обычные ресурсы сайта; это не место для секретов или учётных данных.
Пустая ссылка означает, что установщик пока недоступен. Примеры и установщик
нужно подготовить отдельно; исходный репозиторий не содержит фиктивных загрузок.

`assets:prepare` запускает `scripts/prepare-examples-config.mjs`, который
копирует настройки в `.generated/examples-config.json`, дерево заданий в
`.generated/examples/clark.projects` и создаёт `.generated/examples-manifest.json`.
При повторной подготовке обновляется только собственное дерево примеров;
`.generated/data/default` сохраняется. Vite раздаёт эти файлы в dev-режиме и
переносит их в `dist` при сборке. Относительные ссылки учитывают `BASE_URL`,
в том числе `/clark-editor/` для GitHub Pages. Список содержит версию формата, базовый
URL, пути каталогов и размеры файлов; он находится вне дерева заданий.

В Vite dev/preview файлы примеров обслуживает плагин
`scripts/serve-examples-assets.mjs` по
[контракту HTTP-раздачи примеров](AI_UI_CONTRACTS.md#панель-задания-и-информационные-окна).
Для статического хостинга используются обычные файлы из `dist`.

Если примеры готовятся отдельно, можно обновить комплект сайта после сборки:

~~~bat
node scripts/prepare-examples-config.mjs --source D:\prepared\clark.projects --output dist
~~~

Для уже размещённого дерева можно обновить список на месте, сохранив файлы:

~~~bat
node scripts/prepare-examples-config.mjs --source dist/examples/clark.projects --output dist
~~~

Обе команды также копируют `public/examples-config.json` в выходной каталог.
Поэтому ссылку на облачный каталог задавайте в исходной настройке либо редактируйте
выходной JSON после подготовки.

После изменения файлов примеров повторите подготовку списка и опубликуйте
обновлённое дерево вместе со списком. Если dev server или preview уже запущен,
перезапустите его после подготовки: индекс файлов читается при старте сервера.
Пустой стандартный исходный каталог
допустим: создаётся пустой список, а при установке появляется сообщение, что
примеры ещё не опубликованы. Поле URL облачного каталога в готовом
`dist/examples-config.json` можно изменить без пересборки JavaScript.

Каждый файл скачивается последовательно прямо в локальный файловый поток.
Размер сверяется со списком до завершения записи. Существующие файлы
пропускаются; при прерывании текущий незавершённый файл удаляется, ранее
записанные сохраняются. Свободное место нужно на распакованные файлы примеров;
временное хранилище полного комплекта не требуется. Правила URL и допустимых
путей определены в указанном контракте интерфейса.

Прогресс установки показан под кнопкой «Установить примеры» на её ширину:
«Скачано 3 файла из N». Общее число `N` берётся из списка файлов; счётчик
выполнения увеличивается на один после сохранения файла либо пропуска уже
существующего. Существующие файлы не пересчитываются отдельно, повторная
установка проходит тот же список и дописывает отсутствующее. Прежнего
отдельного блока сообщений о ходе скачивания нет.

Без отметки «Прямая загрузка» кнопка «Скачать установщик решателя» активна при указанной ссылке и открывает
облачный каталог в новой вкладке. Пользователь выбирает там установочный файл
актуальной версии и скачивает его средствами облачного сервиса.
Справка над кнопками поясняет этот порядок. Размер и прогресс загрузки
отображает сервис или браузер; в редакторе нет фиксированного размера,
индикатора или сообщения о скачивании установщика.
Используйте HTTPS (HTTP допускается для localhost), без логина и пароля в URL.
Панель не запускает скачанный файл и не проверяет завершение внешней установки.

Базовая схема поставки ранее сверена с `solver/main` (`55bd862f`): `README.md`,
`docs/AI_BUILD.md` и сценариями `deployment`; описание запуска ярлыком и числа
процессов дополнено текущими согласованными условиями поставки.
Поставка предназначена для Windows x86-64; SFX
создаёт `clark.app` в корне выбранного внутреннего диска, проверяет комплект
и добавляет четыре ярлыка в папку `Clark` на рабочем столе. Для запуска решателя
подготовленный файл со списком заданий перетаскивают на ярлык «Запуск расчета»
либо открывают этот ярлык двойным щелчком: при отсутствии аргумента появляется
стандартный диалог выбора файла со списком заданий.

При установке по умолчанию в `runtime.json` задано четыре параллельных процесса
(`mpiRanks: 4`); число процессов выбирают с учётом числа физических ядер компьютера.
Адрес редактора для ярлыка задаётся поставкой решателя;
`web-gui` не меняет её `runtime.json`.

## Доставка HTML-руководства (4.28.0)

Канонический комплект — `docs/user-guide/`: HTML, CSS, необязательный JS, изображения
и неизменённые JSON-свидетельства исторических сравнений. MD-копии нет.
`scripts/user-guide-assets.mjs prepare` проверяет вход, очищает только собственный
выходной каталог `.generated/user-guide` и копирует все файлы побайтно. Symlink и
пересечение исходного/выходного каталога отклоняются. Vite копирует publicDir в
`dist`; `user-guide-assets.mjs verify` сравнивает пути, размеры и SHA-256 с исходником.
Ошибка подготовки или проверки завершает сборку с ненулевым кодом.

Команда включена в `assets:prepare`, `assets:verify` и оба соответствующих этапа
`scripts/build.mjs`; действуют dev, обычный build, release и Pages. Зависимости
не добавлены. Скрипты справки не включаются в JavaScript SPA. Ресурсы самой
справки используют относительные адреса; вход — `/user-guide/index.html` или
`/clark-editor/user-guide/index.html` для Pages. Якоря не требуют SPA-router.

Caddy раздаёт `/user-guide/*` отдельно от fallback редактора: отсутствующий
ресурс не подменяется `index.html`. Штатный Pages workflow публикует весь `dist`,
поэтому отдельная конфигурация deploy для справки не нужна. Локальную LAN-копию
обновляют обычной сборкой/доставкой; публикация Pages её не меняет.

MED-снимок подготовленной справки переведён из PNG в lossless WebP: размеры
1440×1000 и RGB-пиксели идентичны, оформление не менялось. Остальные изображения
и два JSON-свидетельства перенесены побайтно. Ссылки на подробную GitHub-документацию
требуют сети и соответствующих прав; основной текст и локальные иллюстрации
самодостаточны. CSS печати не является отдельно проверенным PDF.

## Декодер GIF — 4.42.0

Локальная зависимость `gifuct-js` закреплена на версии 2.1.2; транзитивная
`js-binary-schema-parser` фиксируется lockfile. Module Worker собирается Vite
в локальный ресурс с учётом base; CDN, дополнительный сервер и отправка
файлов в сеть не используются. Декодирование по одному кадру описано в
[контракте UI](AI_UI_CONTRACTS.md#управление-просмотром-gif--4420).

Обе MIT-лицензии находятся в `public/third-party-notices.txt`. Поскольку
Editor использует `.generated` как publicDir, маленький build-plugin в
`vite.config.js` включает этот файл в dist через emitFile. Подготовка
библиотек и пользовательской справки остаётся прежней.

## Переход на clark-editor

Репозиторий переименовывается из `web-gui` в `clark-editor` в GitHub Settings.
Подготовленный `build:pages` использует `/clark-editor/`; после переименования
нужна публикация этого комплекта из main и проверка ресурсов по новому адресу.
GitHub перенаправляет адреса репозитория, но прежний адрес Pages не перенаправляет.
Старое имя репозитория не занимать отдельным репозиторием перенаправления.
Ключи localStorage `web-gui:*` намеренно сохраняются; origin сайта остаётся прежним.
В установленном Clark изменить `config/runtime.json`: `dataEditorUrl` =
`https://y26084670-blip.github.io/clark-editor/`. Новый runtime.default.json поставки
уже содержит этот адрес; пользовательские конфигурации не переписываются этой правкой.

### Публикация установщика для прямой загрузки

Достаточно заменить EXE по `solverInstallerUrl` в облаке. При сохранении публичной
ссылки никаких изменений в Editor не требуется. `solverInstallerSize` и
`solverInstallerSha256` удалены из конфигурации; новые загрузчики игнорируют эти
поля даже в старой конфигурации. Сборщик больше не создаёт `.download.json`.
Ранее созданный файл не используется, его можно удалить.

При изменении самой публичной ссылки обновляется только `solverInstallerUrl`.
Для перехода с первоначального загрузчика с SHA-256 нужно обновить установленные
PowerShell-команды через новую упаковку Clark; перекомпиляция Julia не требуется.
