# Интеграция E3D Editor с Clark

Обновлено: 2026-10-22 22:05 UTC+3.

<a id="project-directory-operations"></a>
## Файловые операции проектов — 4.75.0

`runProjectDirectoryOperation` в taskDirectoryService.js создаёт пустой проект,
переименовывает проект или удаляет только пустой проект. Источник — прямой
дочерний каталог выбранного root; root, вложенное задание и заменённый handle
отклоняются. Имена используют тот же переносимый валидатор и запрет перезаписи,
что задания; изменение только регистра имени не выполняется.

Переименование использует общий манифест/SHA-256 и copy → verify → update
references → delete для всего дерева проекта, включая результаты, дополнения
и пустые каталоги. В современных заданиях назначения создаются временные
_nogo.e3d; прежние маркеры сохраняются, добавленные снимаются после успешного
удаления источника. Legacy-задания не получают нового input3XX. Проверяются
копия, неизменность источника и его identity перед удалением. При частичном
сбое проверенная копия сохраняется; error.operationResult сообщает handle,
verified, deletionStarted, sourceRemoved для обновления интерфейса.

В существующем clark.tasks.txt заменяется только полный первый сегмент пути
всех строк проекта с сохранением enabled. Конфликтующие старые пути назначения,
невалидный или изменившийся во время операции список блокируют удаление
источника. Несуществующий список не создаётся. Старый clark.launch.json
инвалидируется и при отсутствии списка. Создание пустого проекта список не
меняет. Удаление пустого проекта убирает его устаревшие строки из списка.

Пустота означает отсутствие любых entries, включая скрытые файлы и пустые
подкаталоги. Перед удалением повторяются проверки пустоты и identity;
сам removeEntry всегда вызывается с recursive=false. Поэтому файл,
появившийся после проверки пустоты, не удаляется этой командой. При сбое
публикации списка каталог сохраняется; частично обновлённый список требует
проверки, операция не объявляется успешно завершённой.

Ограничения File System Access и остановки внешних писателей те же, что у
[команд заданий](#task-directory-operations). Переименование требует места
для полной второй копии проекта. Оно не перенаправляет уже запущенный Clark,
внешние списки/ярлыки и открытые handles других окон. В Viewer после операции
нужно обновить выбор и повторно загрузить задание. Форматы input3XX и solver
не меняются.
[Интерфейс](AI_UI_CONTRACTS.md#project-directory-ui) ·
[Приёмка](AI_VERIFICATION.md#project-directory-verification).

<a id="sketch-request-package"></a>
## Переносимый запрос по эскизу — 4.70.0

`sketchRequestService` формирует ZIP/STORE `clark-sketch-<UUID>.zip`:

| Файл | Содержание |
|---|---|
| README.txt | Порядок передачи и возврата каталога. |
| START.txt | Короткая инструкция для первого сообщения. |
| REQUEST.md | Условие, имена изображений, профиль CLARK и семь действующих схем хранения. |
| context-lock.json | `clark-sketch-request/1`, ID/UTC-время, версия Editor, ревизия/хеш профиля, SHA-256 схем, REQUEST.md и изображений. |
| sketch/01.png и т. п. | Исходные байты выбранных файлов; исходные имена сохранены в manifest. |

`data/ai-context/AI_SKETCH_CONTEXT.md` — побайтовая поставочная копия
`using/packages/sketch-context.md` из clark.knowledge. `source-lock.json`
фиксирует ревизию источника, Git blob и SHA-256; сборщик проверяет SHA-256.
Обновление профиля требует сверки и изменения обоих репозиториев, не сетевого
чтения изменяемой ветки во время запроса.

`sketchContextService` получает семь файлов из `tabRegistry`; использует
`isStoredProperty`, `propertyStoragePath`, `arrayOrder` и настоящий сериализатор.
Дескрипторы включают имена хранимых полей, базовые ограничения, порядок массивов
и примеры формы записи. Вычисляемые UI-поля исключены. `exampleOnlyNotTask`
не является заданием: значения схемы не определяют физическое намерение,
в частности ВТСП. Прикладные функции-валидаторы не транслируются в JSON.
Профиль содержит минимальный контракт локальной ФММ; специальные модели
материалов/геометрии требуют соответствующих дополнительных источников.

Пакет не читает открытое задание, результаты или историю чата. Нет вызова API,
автоматической отправки и автоматического исполнения/импорта ответа модели.
На возврате используется существующий контракт каталога и сохранения.
ZIP ограничен 32 МиБ; имена записей фиксированы/нормализованы, пути обхода и
дубликаты отклоняются. Это writer без распаковки сторонних архивов.
[UI](AI_UI_CONTRACTS.md#sketch-request-ui) ·
[Проверки](AI_VERIFICATION.md#verification-sketch-request).

<a id="shared-project-disk"></a>
## Общий доступ к диску Editor/Viewer — 4.69.0 / 4.48.0

`projectDiskAccessService.js` одинаков в обоих GUI. Editor сохраняет выбранный
`FileSystemDirectoryHandle` в IndexedDB `clark.project-disk.v1`, версия 1,
object store `access`, ключ `disk`, запись `{version:1, handle}`. Это доступ
браузера; абсолютный путь и привязки локального решателя здесь не хранятся.
Общий origin и один профиль браузера обязательны; разные пути Pages допустимы.

После завершения записи BroadcastChannel `clark.project-disk.v1` передаёт
`{version:1,type:"changed"}`. Viewer читает сохранённый handle при старте,
фокусе или уведомлении, только если диск ещё не выбран. Проверяет
`queryPermission({mode:"readwrite"})`; при granted перечисляет непосредственные
`clark.*`, кроме `clark.app`, тем же сервисом. Иначе предлагает отдельную кнопку:
`requestPermission({mode:"readwrite"})` вызывается только из щелчка. Системный
выбор другого диска доступен независимо от сохранённого доступа и также
сохраняет handle. Ошибка IndexedDB не отменяет уже открытый локальный диск.
Ожидание хранилища ограничено пятью секундами; соединения и каналы закрываются.

Выбор дочернего каталога, проекта, задания и загруженная модель принадлежат
каждому GUI. Изменение общего диска не переключает существующий выбор другой
вкладки. Позднее восстановление не заменяет ручной выбор. Editor по-прежнему
открывает панель выбора диска при старте/F5. Обработчик `clark://` и маркеры
workspace не меняются от сохранения доступа в браузере.

Проверка: `scripts/check-shared-disk-browser.mjs`, `VIEWER_ROOT` указывает на
совместимую рабочую копию Viewer. Реальные IndexedDB/OPFS и две вкладки;
системный picker и состояния разрешения моделируются. Нативные права Windows
требуют проверки на компьютере пользователя.


<a id="catalog-binding"></a>
## Связывание каталогов выбранного диска — 4.68.0

`projectDiskAccessService.js` перечисляет непосредственные каталоги выбранного диска
по маске `clark.*`, исключая `clark.app`. Выбранный дочерний handle остаётся
обычным базовым каталогом для истории, `clark.tasks.txt`, операций и канала Viewer.
Абсолютный путь браузеру не требуется. Сам выбор диска не меняет привязки.

«Связать с Решателем» пишет в выбранном диске `clark.catalogs-request.json`:
`{schemaVersion:1, requestId:<GUID>, catalogs:[{name,workspaceId:<GUID>},...]}`.
Идентификаторы новые для каждой попытки. URI:
`clark://bind-catalogs?request=<requestId>&name=<имя диска>`.
Если после записи утрачена активация пользователя, подготовленная URI ожидает
повторного щелчка. До ответа повтор используется без переписывания запроса.

Обновлённый `Invoke-ClarkProtocol.ps1` просит один раз выбрать тот же диск,
сверяет requestId, проверяет все имена и создаёт обычную привязку schemaVersion 1
для каждого каталога. Старые `bind/run/settings/conditions` сохраняются.
Ответ в `clark.catalogs-result.json` содержит schemaVersion, requestId,
state (`bound`/`error`), catalogs (только успешно записанные `{name,workspaceId}`),
message. Полный успех требует всех ожидаемых пар без повторений; чужой requestId
игнорируется. Запрос одноразовый, включая частичную ошибку. Editor перечитывает
маркер текущего каталога; при переключении читает маркер выбранного каталога.
Для добавленных позднее каталогов пользователь повторно выбирает диск и связывает
обновлённый список. Старый локальный обработчик требует обновления; обновление
только веб-страницы не добавляет команду `bind-catalogs`.

<a id="hts-naming"></a>
## Переход HTC → HTS — 4.44.3

Новые general.txt содержат `htsRegimFC`, `htsMu`, `htsRo`;
прежние ключи читаются как aliases с приоритетом канонического ключа по наличию.
[Контракт сериализации](AI_DATA_CONTRACTS.md#hts-storage-aliases).
Новые данные требуют согласованного обновления solver и Viewer.
Старый исполняемый файл, читающий только HTC-ключи, для новых файлов не подходит.

Базовая библиотека и новые локальные записи используют `xapLibHTS`.
При чтении локальной ВТСП-библиотеки каждый материал сначала ищется в
`input3XX/xapLibHTS`, затем в прежнем `input3XX/xapLibHTC`.
Наличие канонического каталога не скрывает остальные legacy-материалы.
Имена сопоставляются без учёта регистра и с Unicode NFC, как при проверке ссылок.
Для одинакового имени каноническая запись имеет приоритет.

Загруженная локальная запись сохраняет фактический `relativePath` и `sha256`;
скрытая одноимённая legacy-запись также сохраняется как SHA-снимок.
Явное сохранение записывает каноническое имя каталога и удаляет проверенный
legacy-источник; удаление учитывает обе записи, чтобы старая характеристика
не появилась снова при следующей загрузке. Изменение исходника либо появление
конфликтующего файла после загрузки требует повторного чтения. Импорт и
копирование из базы проверяют конфликты с legacy-файлами до записи в HTS.
Файловая система не предоставляет атомарной транзакции или блокировки внешних
писателей; действующее требование остановить внешние изменения сохраняется.

Исходные активные demo/примеры переведены на новые имена. Генераторы ресурсов
заново создают индексы и SHA-256, хеши не исправляются вручную. Датированные
отчёты, evidence, source-lock и ссылки на старые commit сохраняют исходные имена.
Переименование не меняет числовые параметры, материальные законы и бинарные данные.


Версия 4.31.0 сохраняет CF_FMMEPS/CF_HTSEPS (по 0.01 по умолчанию) вместо
устаревших параметров нулевого шага и локальной дихотомии. Требуется обновлённый solver:
старый строгий загрузчик не знает новые ключи. Новый solver читает старые ключи
как игнорируемые. Legacy-импорт в solver задаёт оба новых допуска для обоих профилей.
[Алгоритм поиска](https://github.com/y26084670-blip/solver/blob/main/docs/AI_NUMERICAL_CONTRACTS.md#nc-magnetic-source-search).
Глобальный Newton JWeak1 этой правкой не меняется.

## Стыковка с расчётным модулем
Проект `web-gui` является источником истины исключительно для формата файлов
исходных данных `input3XX`: имён каталогов и файлов, состава и имён JSON-ключей,
структуры и вложенности JSON, порядка записей, а также порядка и ориентации
сериализованных данных. Решатель на Julia обязан читать и писать этот формат.

Проект `solver` является источником истины для математических алгоритмов,
физических понятий, семантики значений, формул, вычисляемых величин и правил
математической интерпретации исходных данных. Перенесённая в GUI вычислительная
логика должна соответствовать реализации Julia.

Подтверждённый дефект исправляется в проекте, которому принадлежит
соответствующая ответственность. Наличие дефекта не изменяет границы
ответственности и не переносит статус источника истины другому проекту.

Соответствие файлов и вкладок:

| Файл           | Вкладка             | Хранение |
|----------------|---------------------|----------|
| general.txt    | Общие параметры     | CLUSTER  |
| conrab.txt     | Конфигурация модели | RECORDS, при сохранении ровно 2 записи |
| kvs.txt        | Элементы модели     | RECORDS  |
| tks.txt        | Области наблюдения  | RECORDS  |
| amplitudes.txt | Импульсы            | RECORDS  |
| moves.txt      | Траектории          | RECORDS  |
| mhj.txt        | Заданные источники  | RECORDS  |

Графики импульсов и траекторий и генератор временных зависимостей являются
пользовательскими представлениями. Их подробный контракт находится в
[`AI_UI_CONTRACTS.md`](AI_UI_CONTRACTS.md#графики-и-генератор-временных-зависимостей).
Файлы истории формул принадлежат `input3XX`, но не входят в BaseModel и общую
команду сохранения задания.

Актуальный `conrab.txt` содержит две JSON Lines-записи с одинаковым полным набором
из 12 актуальных полей: первая задаёт профиль Float32, вторая — Float64.
`GEO_ANGLE` принадлежит геометрической проверке редактора; остальные 11 — solver.
Редактор сохраняет угловой допуск в обеих строках. Старые файлы получают 0.1°
из схемы; применяет проверку профиль, выбранный `general.doubleFloat`.
[Точный контракт](AI_DATA_CONTRACTS.md#geometry-measurement-diagnostics).

Для загрузки сохранённого новой оболочкой файла нужен solver, игнорирующий
неизвестные ключи `Conrab` без отдельного списка разрешений. Решатель не хранит
и не использует `GEO_ANGLE`; проверка собственных полей сохраняется. Штатный
расчёт не переписывает `conrab.txt`. Явный экспорт `write3XX`/повторный legacy-импорт
формирует только поля решателя: после него отсутствующий угловой допуск редактор
снова дополнит значением 0.1°. Это не канал сохранения настроек редактора.
При чтении допускается одна корректная JSON-объектная запись: `dataService.load`
выдаёт предупреждение и до десериализации создаёт две независимые копии её
значений. Обе профильные колонки доступны для редактирования. После успешного
преобразования загрузчик сообщает `loadState.requiresSave = true`, и вкладка
сразу получает явный dirty-признак. Он сохраняется после Undo и снимается
после успешной записи обеих строк. Исходный файл при загрузке не изменяется.
Пустой файл, пустая или лишняя запись, некорректный JSON и значение, не являющееся
объектом, остаются ошибками загрузки.

Логическое поле `startITER` отображается как `StartITER` и независимо задаётся
для обоих профилей. `true` означает нулевые значения в качестве начального
приближения итерационного процесса, `false` — значения предыдущей итерации.
Значение по умолчанию — `false`. Если ключ отсутствует, обычная десериализация
подставляет это значение, а диагностика загрузки сообщает об отсутствующем
свойстве. При сохранении ключ `startITER` записывается в обе строки как JSON
boolean. Редактирование, история и индикация изменений используют общий механизм
схемы. Чтение таких файлов решателем требует поддержки `startITER` в его `Conrab`
и JSON-контракте; прежний решатель со строгим набором из 12 полей их не принимает.

Это поведение дополнения одной записи включено только настройкой
`singleRecordFallback` схемы `conrab`.
`recordCount: 2` продолжает строго задавать форму BaseModel и сохраняемого файла.
При явном сохранении сериализуются обе записи в порядке Float32 → Float64,
включая отличающиеся значения; выбранная разрядность не исключает второй профиль.
В BaseModel профили сохраняют обычную RECORDS-форму; только представление
транспонирует их в таблицу `Параметр | Float32 | Float64`. Структурные операции
над двумя фиксированными записями запрещены, а редактирование любой профильной
ячейки проходит через обычную историю вкладки.

Колонка актуальной разрядности выделяется тонкой синей рамкой: при
`general.doubleFloat = false` — Float32, при `true` — Float64. Выделение
обновляется по публикации модели общих параметров, в том числе после Undo/Redo,
и восстанавливается после перерисовки таблицы. При отсутствии корректного
значения разрядности рамка не выводится. Это состояние представления само по
себе не изменяет профили, их историю, dirty-признак или сериализацию.

Удалённые из конфигурации поля отсутствуют в свойствах схемы, BaseModel,
таблице редактора и результате сохранения. При чтении старых заданий
`obsoleteStoragePaths` позволяет молча игнорировать известные устаревшие
ключи; их значения не переносятся в модель. Исходный файл при загрузке
не изменяется, а после явного сохранения обе записи содержат только
актуальные поля. Диагностика прочих неизвестных или отсутствующих
обязательных ключей сохраняется.

Для сохранённого локального поиска ВТСП `EPSILON5 = 5 * eps(REAL)`, где `REAL` —
выбранный тип Float32 или Float64. Действуют следующие назначения:

| Поле | Назначение в текущем решателе |
|---|---|
| `KB1` | Множитель нижней границы `J`: `b1 = EPSILON5 * KB1`. |
| `KEPS1` | Порог начальной ширины диапазона `J` для запуска поиска, А/мм². |

Верхняя начальная граница — `b2 = JC0`. Условие `abs(b2-b1) > KEPS1`
проверяется перед циклом поиска и не является критерием его завершения по
текущей ширине интервала. Пробное значение задаёт плотность тока `J`; удельное
сопротивление вычисляется непосредственно как `ρ(J)` в `HTS_JSP_ro`.

Назначения относятся к сохранённой функции локального поиска, а не к текущему глобальному циклу J/λ. Полный Newton использует аналитическую касательную E(J) и не вызывает HTS_JSP_iterator в Ist. Историческая реализация: [Julia][hts-current-implementation].
Двухпрофильный JSON-формат и редактируемость актуальных полей сохраняются.

[hts-current-implementation]: https://github.com/y26084670-blip/solver/blob/f1724138d3c907af814fea06c8d4b88801004216/src/core/02_model_htc.jl

`mhj.txt`, если существует, содержит ровно одну RECORDS-запись `{ v }`.
Одна строка JSON Lines физически совпадает с одиночным JSON-объектом, который
читает решатель; вторая запись недопустима, поскольку решатель её не прочитает.
Схема файла необязательна. При отсутствии файла и нулевом требуемом числе строк
BaseModel вкладки остаётся `null`, поэтому обычное сохранение файл не создаёт.
Существующий файл автоматически не удаляется.

### Библиотеки характеристик

Для загруженного задания обе вкладки начинают с локального источника; базовые
характеристики пользователь выбирает явно. Отсутствие локальных записей или
ошибка доступа не разрешают подменять ими локальную библиотеку. Это правило
просмотра не изменяет поиск характеристик решателем. Подробный UI-контракт:
[начальный источник](AI_UI_CONTRACTS.md#material-source-selection); практика —
[Руководство](user-guide/index.html#material-source).


Каноническая базовая библиотека редактора находится в tracked-каталоге
`data/default` и включается в статические ресурсы сборки через детерминированный
индекс и контрольные суммы SHA-256. Она содержит `xapLibFMM` и `xapLibHTS`,
доступна только для чтения и не требует серверного API.
Индекс запрашивается без использования устаревшей браузерной копии. URL каждого
файла характеристики содержит его SHA-256, поэтому неизменившиеся файлы могут
кэшироваться, а новая версия всегда получает новый URL. В конфигурации Caddy
`/data/default/*` обслуживается только как статический ресурс и при отсутствии
файла возвращает HTTP 404, не подменяясь страницей `index.html`.

Последние две вкладки приложения — «Характеристики ФММ» и «Характеристики
ВТСП». Они зарегистрированы отдельно от `tabRegistry`, поэтому не загружаются
как часть задания, не сохраняются общей командой и не используют историю
BaseModel задания. Несохранённые правки локальных библиотек ведут отдельную
Undo/Redo-историю каждой библиотечной вкладки.
Обе вкладки используют RECORDS-таблицу характеристик и `DetailRegion`: ФММ
показывает таблицу H–M из 12 строк, ВТСП — таблицу скалярных параметров.
Выделенные характеристики ФММ одновременно отображаются линейными графиками
M(H), по одному набору данных и элементу легенды на характеристику.
Горизонтальный разделитель регулирует высоту общей нижней области ФММ, а
вертикальный — соотношение ширины таблицы H–M и графика. Оба разделителя
поддерживают перетаскивание указателем и управление клавишами со стрелками.
Встроенный 3D-viewer исходной геометрии входит в runtime-контракт и
описан в разделе «3D-визуализация исходной геометрии». Отдельный
viewer расчётных HDF5-результатов остаётся последующим направлением.

Выделенные базовые характеристики копируются побайтово только в
`input3XX/xapLibFMM` или `input3XX/xapLibHTS` выбранного задания. Совпадающий
локальный файл не перезаписывается; отличающийся файл заменяется только после
явного подтверждения пользователя. Браузерный legacy-импорт полностью разбирает
и проверяет `XAP.lib` из корня задания до начала пакетной записи, а затем создаёт
JSON-файлы в локальной библиотеке ФММ. Пользовательский legacy-импорт ВТСП
отсутствует. Конфликт всего пакета определяется до первой записи. Для копирования
требуется единое явное подтверждение; в выборочном импорте ФММ замена входит
в действие кнопки и явно описана в её подсказке.
Подтверждение привязано к точному набору путей и SHA-256; изменение файла между
диалогом и повторной проверкой требует нового подтверждения. File System Access
API не предоставляет атомарную транзакцию для нескольких файлов, поэтому ошибка
носителя после начала записи показывается как частичное выполнение с числом
завершённых, ошибочного и оставшихся файлов. Ни копирование, ни импорт не изменяют
базовую библиотеку.

Обе библиотечные вкладки переключаются между базовой readonly-библиотекой и
локальной библиотекой задания; перед асинхронной загрузкой нового источника
строки старого источника удаляются. Очистка и заполнение Tabulator выполняются
последовательной очередью: завершившаяся позднее операция старого источника не
может перекрыть новый выбор. Базовые строки всегда readonly. Для локальных ФММ
непосредственно редактируются название, `hip`, комментарий и 12 пар H–M;
добавление, удаление и перестановка строк H–M запрещены. Для локальных ВТСП
редактируются название, комментарий и все текущие скалярные параметры; число и
состав строк параметров фиксированы схемой. Изменения накапливаются в
представлении и записываются отдельной командой «Сохранить».

Проекция ВТСП содержит только 18 текущих параметров. Legacy-поля `m2_dh`,
`m2_dm`, `m2_n` в редактируемую модель не переходят. Если перенесённый файл не
содержит более новых параметров, применяются defaults конструктора `PropHTS`
решателя: `j_ani = true`, `KHabc = 1`, `Diag = 0`, `M3D = false`. При сохранении создаётся
нормализованный JSON только с текущими полями.

После `JCb` и перед `j_type` расположен логический параметр `j_ani` с подписью
«Тип токовой подсистемы»: `true` — «Планарная», `false` — «Изотропная».
Описание: «true - планарная модель электропроводящих свойств с нулевой X компонентой
в плоскости анизотропии, false - изотропные электропроводящие свойства».
Старые характеристики без поля получают `true`; явное `false` не заменяется
значением по умолчанию. При сохранении принимаются только логические значения,
а внутренний legacy-парсер config.txt версий 201–204 устанавливает `true`.
Наличие и сохранение поля не подтверждают поддержку изотропного расчёта:
состояние подключения вычислительных ветвей принадлежит
[контракту solver](https://github.com/y26084670-blip/solver/blob/main/docs/AI_NUMERICAL_CONTRACTS.md#nc-vtsp).

Правка ячейки основной или детальной таблицы создаёт одно действие общей для
данной библиотечной вкладки последовательности Undo/Redo. История действует
только для локального источника и хранит несохранённое состояние представления,
не включая характеристики в BaseModel задания. Она очищается после успешного
сохранения, импорта или удаления, а также при смене источника, задания или
перезагрузке библиотеки: сохранённые SHA-256 файлов не должны восстанавливаться
из устаревшего снимка истории.

Изменение названия переименовывает JSON-файл. Перед записью проверяются SHA-256
исходной версии и отсутствие другого файла с новым именем; исходный файл
удаляется только после успешной записи нового. Удаление выбранных характеристик
требует подтверждения в модальном окне. Команда «Импортировать» в локальном источнике ФММ использует выборочный
импорт по текущим элементам; см. [единый контракт](#task-import-used-fmm).
Наличие локальной `XAP.lib` проверяется без сравнения отпечатка с базовой.
Legacy-импорт ВТСП не предоставляется: локальная библиотека ВТСП формируется
копированием базовых JSON-характеристик либо редактированием уже находящихся в
`input3XX/xapLibHTS` файлов. Проверки SHA-256 конфликтов и конкурентного
изменения локальных JSON-файлов сохраняются как независимый контракт
безопасности записи.
Изменения библиотек имеют отдельную реактивную ревизию и не перезагружают
BaseModel задания.

`elements.xapName` является readonly-колонкой. Команда «Выбрать характеристику»
панели вторичной функциональности выбирает локальную библиотеку по первой
по времени выделения строке из текущего `getSelectedRows()`: ФММ
(`input3XX/xapLibFMM`) для `model ∈ {0, 1}` и ВТСП (`input3XX/xapLibHTS`)
для `model = 2`. Положение строки в таблице не определяет этот выбор.
После снятия выделения и повторного выбора строка попадает в конец списка.
Смешанное выделение разрешено: одно выбранное имя без `.txt` назначается всем
выделенным элементам одной публикацией BaseModel и одним действием Undo/Redo.
Значение `model` при назначении имени не изменяется.

Общая проверка модели перед синхронным обходом `modelRegistry`
асинхронно читает фактические локальные библиотеки задания. Для каждого
непустого `elements.xapName` библиотека выбирается по `model` самой строки:
ФММ при `model ∈ {0, 1}`, ВТСП при `model = 2`.
Отсутствующий файл, наличие имени только в библиотеке другого вида и
неоднозначные регистронезависимые варианты имени создают отдельный ERROR
с адресом строки `elements.xapName`. Базовые библиотеки при этой проверке
не используются. Ошибка чтения локальной библиотеки также запрещает ложный
успешный результат проверки и отображается в общей диагностике.

Числовые значения `elements.targ` сохраняются: `0` отображается как `Unknown`,
`1` — `M - const`, `2` — `J - const`, `3` — `Virtual`. Подсказка заголовка
«Назначение элемента» содержит строки:

```text
Роль элемента в расчетах:
Unknown -> Неизвестные источники
M-const -> Заданная намагниченность
J-const -> Заданная плотность тока
Virtual -> Виртуальный (поле/катушка)
```

Текстовые подсказки `TableBuilder` сохраняют явные переносы строк. Их
содержимое остаётся текстом DOM-узла и не интерпретируется как HTML.

Сведения, которые GUI не выводит самостоятельно и получает из решателя:

- состав и имена ключей каждого файла;
- ориентация развёртки плоских массивов относительно таблиц редактора;
- состав перечислений и соответствие «значение — подпись»;
- правила интерпретации geo в зависимости от geoType;
- перечень производных величин и формулы их вычисления;
- какие величины вычисляет решатель, а какие обязан подготовить редактор.

### Ориентация развёртки плоских массивов

Хранимый плоский ARRAY рассматривается как двумерное значение 1×N.
При отображении он преобразуется в таблицу с числом колонок `nColumns`.
Атрибут дескриптора `order` определяет именно это преобразование, а не вводит
отдельный тип одномерного массива:

- `order: "column"` — значения плоского хранения заполняют колонки таблицы;
- `order: "row"` — последовательные группы по `nColumns` образуют строки;
- при отсутствии `order` используется `"column"`, что сохраняет поведение
  существующих схем.

Поэтому `geo` остаётся плоским значением в StorageModel, формально 1×N, но
для табличного представления его последовательные тройки образуют строки
8×3 или 4×3 и описываются `order: "row"`.

| Поле                                          | Форма                                         | Ориентация                               |
|-----------------------------------------------|-----------------------------------------------|------------------------------------------|
| `impuls` (amplitudes)                         | n×2                                           | column-major                             |
| `angle` (moves)                               | n×4                                           | column-major; колонки: Время, aX, aY, aZ |
| `position` (moves)                            | n×4                                           | column-major; колонки: Время, X0, Y0, Z0 |
| `v` (mhj)                                     | n×3                                           | column-major                             |
| `geo` (kvs, `geoType = 0`)                    | 8×3                                           | row-major                                |
| `geo` (tks, `geoType = 0`)                    | 4×3                                           | row-major                                |
| `geo` (прочие `geoType`)                      | плоский набор параметров                      | —                                        |
| `dr`, `vkan`, `sym.vi`, `sym.r0`, `dp`, `med` | плоский вектор                                | —                                        |
| `src/services/solver/kvDerived.js::nodeCount` | `src/core/types.jl` (`Amplitude.n`, `Move.n`) | пересчёт `n` по числу строк              |

Хранимое вычисляемое поле `n` не показывается в основных таблицах, но
остаётся обязательной частью StorageModel и пересчитывается перед записью:

- `Amplitude.n = impuls.length` в BaseModel;
- `Move.n` равно общему числу строк `angle` и `position`;
- для валидной записи `angle.length === position.length === Move.n`;
- при несовпадении длин `Move.n` получает нейтральное значение `0`, а
  запись остаётся ошибочной. GUI не выбирает одну из таблиц источником истины
  и не добавляет или удаляет строки автоматически.

Правило приоритета формата: для строк таблицы, описывающих форму и ориентацию
данных на диске, при расхождении сериализации GUI и чтения или записи Julia
корректным считается формат GUI; исправлению подлежит код ввода-вывода Julia.
Это правило не распространяется на `nodeCount`, математические алгоритмы и
семантику значений: для них источником истины является Julia.
Сопоставляемые участки реализации Julia: `src/base/01_common.jl::fcopy`
(column-major), `src/core/03_kv.jl::unpack` (`reshape(geo,(3,8))`).

### Вариантное представление и смена geo

Каноническая длина валидного хранимого `geo` постоянна и не зависит от
`geoType`: 24 значения для `kvs` и 12 для `tks`. После преобразования
`arrayShape` каноническая форма BaseModel составляет соответственно
матрицу 8×3 или 4×3 с `order: "row"`. Укороченное входное значение не
нормализуется молча; его отдельная диагностика относится к рабочей схеме.

Для `geoType = 0` связанное представление показывает матрицу вершин с
колонками X, Y, Z. Для параметрических вариантов codec разворачивает
BaseModel через `arrayShape`, показывает значащий префикс как фиксированные
именованные строки с одной колонкой и при обратном преобразовании дополняет
хвост буфера нулями. Неизвестный строго типизированный `geoType` использует
сохраняющее матричное представление: значение не переинтерпретируется и не
стирается.

Вариант выбирается по объявленной зависимости `geoType`.
`property.variantCodec` содержит непустой `dependencies`, чистые
`decode` и `encode`, а при необходимости —
`onDependencyChange`. Последняя функция вызывается модельным слоем, а не
View. Для `geo` смена одного известного `geoType` на другой известный
тип обнуляет весь буфер, поскольку одинаковые позиции имеют несовместимую
семантику в разных вариантах. Переход к неизвестному значению использует
сохраняющий fallback и не стирает буфер. Реакция выполняется независимо от
того, открыто ли связанное представление.

Строки `geo` семантически фиксированы, поэтому схема объявляет
`rowsMutable: false`. Панель не показывает структурные команды, а общий
обработчик операций дополнительно запрещает их выполнение.

`unpackKvVertices` и `unpackTkVertices` используются только для получения
производных вершин. Для редактирования параметрических вариантов они
неприменимы: обратного преобразования вершин в исходные параметры нет.

Источник состава и длины значащего префикса:
`src/core/03_kv.jl::unpack`, `src/core/03_tk.jl::unpack`.
Полный сброс является политикой GUI, принятой из-за несовместимой семантики
одинаковых позиций разных вариантов.

### Требования решателя к порядку записей

- Записи `kvs.txt` располагаются группами по возрастанию `targ`: 0, 1, 2, 3.
  Решатель адресует записи срезами `kvs[1:NV1]`, `kvs[NV1+1:NV]`; нарушение
  порядка не диагностируется и даёт неверный расчёт.
- Внутри группы `targ = 0` записи с `model = 2` (ВТСП) предшествуют остальным проводящим.
- Требуемое число строк `mhj.v` равно сумме `eoCount` записей с
  `targ ∈ {1, 2}`. Во время редактирования фактическое число строк
  хранимого `v` может отличаться. При доступной BaseModel `elements`
  проверка модели сообщает об этом как об ERROR с фактическим и требуемым
  числами строк, но не блокирует загрузку, редактирование или сохранение
  и не изменяет `v` автоматически.

Источник: `src/task/01_counters.jl::evalCounters`, `src/vsolver/04_mhj.jl::mhjRecall!`.

### Состав таблицы заданных источников (mhj)

Строки образуются последовательным перебором записей `kvs` с `targ = 1`,
затем `targ = 2`, сплошным потоком без разделения групп. Порядок внешней
записи и вложенных циклов:

    KV (полный массив elements) →
    D12 (kv.dp[1]) → D13 (kv.dp[2]) → D15 (kv.dp[3]) →
    LS (kv.sym.ls) → AS → PS

Границы AS и PS принимают значения `kv.sym.as` и `kv.sym.ps` только для
геометрического типа симметрии (`kya = 0`, `kyp = 0`); в остальных случаях — 1.

Колонки таблицы:

| Колонка                    | Содержание                                                   | Вычисляемая |
|----------------------------|--------------------------------------------------------------|-------------|
| `№ ЭО`                     | сплошной 1-based номер ЭО внутри текущей записи `elements`   | да          |
| `№ ЭО общий`               | номер ЭО с учётом всех физически предшествующих элементов     | да          |
| `KV`                       | 1-based номер записи в полном массиве `elements`             | да          |
| `D12`, `D13`, `D15`       | индексы разбиения вдоль направлений рёбер 1–2, 1–3 и 1–5     | да          |
| `LS`                       | номер образа локальной симметрии                              | да          |
| `AS`                       | номер геометрического азимутального образа                    | да          |
| `PS`                       | номер геометрического периодического образа                   | да          |
| `Mx [кА/м] / Jx [А/кв.мм]` | x-компонента `v`                                             | нет         |
| `My [кА/м] / Jy [А/кв.мм]` | y-компонента `v`                                             | нет         |
| `Mz [кА/м] / Jz [А/кв.мм]` | z-компонента `v`                                             | нет         |

Порядок индексных колонок точно соответствует вложенности циклов
`mhjRecall!`: `KV → D12 → D13 → D15 → LS → AS → PS`; индекс `PS`
изменяется быстрее всего. `№ ЭО` увеличивается в том же порядке и
сбрасывается для каждой записи `elements`. `№ ЭО общий` равен локальному
номеру плюс сумма `eoCount` всех физически предшествующих записей
`elements`, независимо от их `targ`; поэтому в таблице источников возможны
разрывы глобальной нумерации. `LS`, `AS` и `PS` являются номерами
образов, а не общим числом образов.

Смысл величины определяется `targ` записи `kvs` (намагниченность либо плотность
тока); разделения строк по `targ` в таблице нет.

Источник: `src/vsolver/04_mhj.jl::mhjRecall!`, `src/core/03_kv.jl::limits`.

### Вычисляемые колонки ARRAY-представления

ARRAY-свойство может объявить отдельный descriptor представления:

```js
computedView: {
    dependencies: ["elements"],
    columns: [
        { key: "kv", label: "KV" },
        // ...
    ],
    rows({ models, property, rowLimit }) {
        return sourceRows.slice(0, rowLimit);
    },
}
```

`dependencies` содержит уникальные идентификаторы других вкладок.
`rows` — чистая синхронная функция, получающая копии только объявленных частей
BaseModel, статический descriptor свойства и `rowLimit` — фактическое число
строк хранимого ARRAY-представления. Она возвращает не более `rowLimit`
объектов и не обязана материализовать неотображаемый хвост внешней раскладки;
`columns` задаёт уникальный ключ, подпись и необязательное описание каждой
вычисляемой колонки. Значения вычисляемых ячеек являются скалярными данными
ViewModel.

Локальную форму descriptor проверяет `createSchema`; после сборки
`tabRegistry` отдельная контрактная проверка подтверждает существование всех
вкладок-зависимостей. `computedView` не является `compute` или
`computeStored`: он не создаёт свойства BaseModel и не участвует в графе
модельного пересчёта.

`TableView` помещает вычисляемые readonly-колонки перед редактируемыми
колонками значения. Они не получают editor или validator, не входят в строки
BaseModel и не сериализуются. Внутренняя идентичность строки остаётся отдельным
transient-полем и не выводится из вычисляемых значений.

Число редактируемых строк определяет только хранимое ARRAY-значение. Строки
внешнего источника присоединяются позиционно: лишние строки источника не
материализуются, а при их нехватке вычисляемые ячейки остаются пустыми.
Изменение внешней вкладки обновляет только вычисляемые значения; оно не
добавляет, не удаляет, не переставляет и не перепривязывает хранимые строки.

Подпиской на ревизии объявленных внешних вкладок владеет `DataEditor`.
Он передаёт `TableView` актуальный снимок через контекст представления и
обновляет активный `TableView` независимо от его размещения. `TableView`
не импортирует и не подписывает `modelService` непосредственно. Поскольку
вычисляемые значения не хранятся в строках Tabulator, изменение их сигнатуры
явно переформатирует только ячейки readonly-колонок `computedView`; общий
`redraw` не считается достаточным. Для скрытой вкладки переформатирование
откладывается до восстановления видимости.

Схема может объявить основную View-проекцию:

```js
views: {
    main: { property: "v" },
}
```

`views.main.property` ссылается на единственное свойство RECORDS-схемы.
Свойство обязано быть ARRAY с `view: TABLE`. В этом режиме его `TableView`
занимает основную область вкладки непосредственно: внешняя RECORDS-оболочка
не отображается строкой со summary и `DetailRegion` для свойства не создаётся.
Это только проекция View; BaseModel `[{ v }]`, StorageModel, сериализация и
файловый формат не меняются.

Для optional-файла состояния `null` и `[]` дают пустую основную таблицу
независимо от schema-default и не материализуют запись. Первое явное добавление
строки создаёт одну запись `[{ v }]`; удаление последней строки уже созданной
записи оставляет `[{ v: [] }]`. Значение с более чем одной RECORDS-записью
либо записью, где выбранное свойство не является ARRAY, не проецируется молча:
основное представление блокирует изменение, данные сохраняются в BaseModel, а
прикладной валидатор сообщает ERROR.

Поскольку у основной проекции отсутствует родительская ячейка-summary,
ARRAY-level ограничения `minItems`, `maxItems` и `uniqueItems` в этом
режиме пока не поддерживаются и отклоняются `createSchema`. Ограничения
`property.items` продолжают действовать в редактируемых ячейках View.

Для `mhj` функция источника — `mhjRows(elements)`, а `views.main` проецирует
`v` как основную таблицу. Если требуемое число строк положительно, а
единственная запись `mhj` отсутствует, прикладной валидатор создаёт ERROR.
Существующий файл с нулём или более чем одной RECORDS-записью также ошибочен.
Для структурно корректной записи `[{ v }]` при доступной BaseModel `elements`
валидатор сравнивает `v.length` с `mhjRowCount(elements)`. Несовпадение
является ERROR, но не переводит основную проекцию в readonly-состояние, не
мешает сохранению и не добавляет, не удаляет, не переставляет и не
перепривязывает строки. Пользователь самостоятельно согласует `v` с
параметрами элементов и повторно запускает проверку модели.

Запуск импорта из оболочки передаёт `action=import` нативному Clark; бинарный
`MHJ.in` читает импортёр solver (`src/import/01_dictFromData2XX.jl::importMHJ`).
Он переносит фактически записанные векторы, включая полностью нулевые строки,
в `input3XX/mhj.txt`. Десериализация и ARRAY-проекция редактора также сохраняют
нулевые строки. Отсутствующий хвост не считается неявным набором нулей:
ни импортёр, ни редактор не дополняют его по числу ШГ. Требуемое число строк
определяют назначения, дискретизация и симметрия из `kvs.txt`; один `MHJ.in`
не содержит привязки векторов к конкретным ШГ. Разбор воспроизведён в
[проверке от 29.09.2026](AI_VERIFICATION.md#verification-geometry-values-mhj).

После каждой ревизии `elements` вычисляемые индексы обновляются автоматически.
Если текущая раскладка короче загруженного `v`, оставшиеся вычисляемые ячейки
остаются пустыми: GUI не создаёт несуществующие итерации решателя. Равенство
числа строк не доказывает смысловую привязку после перестановки элементов;
автоматическое восстановление такой привязки не выполняется.

Правило: математическая и физическая интерпретация данных не восстанавливается
по комментариям и образцам файлов. При отсутствии сведений работа
останавливается и запрашивается уточнение по коду решателя. Формат файлов при
этом определяется проектом GUI и не выводится из реализации Julia.

### Перенесённая математика решателя
Часть алгоритмов решателя воспроизводится в GUI как js-код: распаковка
геометрии, развёртка массивов, вычисление производных величин.

Такие модули размещаются в services/solver/ и подчиняются правилам:

- модуль содержит только вычисление: он не читает файлы, не обращается к схеме, не знает о
  Tabulator и не хранит состояние;
- каждая перенесённая функция снабжается ссылкой на источник: файл и имя функции julia,
  версия или дата снимка;
- перенос выполняется по исходному коду решателя, а не по комментариям, документации или
  образцам файлов;
- расхождение js-реализации с julia-оригиналом считается дефектом GUI независимо от того,
  какая из реализаций «удобнее».

Схемы вкладок вызывают эти функции в дескрипторах вычисляемых свойств и в кодеках

## Список заданий и локальный запуск Clark

`Tasks` открывает `TaskLaunchWindow` кнопкой «Формирование списка заданий и запуск
приложений» под загрузкой задания.
Кнопки находятся в отдельной нижней области панели вне прокрутки;
длинный список заданий прокручивается внутри оставшейся высоты. В малом окне
верхняя область выбора также допускает прокрутку, не сдвигая кнопки запуска.
Под выбором каталога краткая инструкция и мигающий статус связи занимают
одну строку; при недостатке ширины уменьшается её шрифт.
Окно использует общий `FloatingWindow`, сохраняет положение и размер, содержит
список с множественным выделением, команды обновления и включения/отключения,
запуск solver/modelica/import. Прежняя кнопка Julia-клиента убрана;
актуальная поставка отклоняет прежнее действие `circuit`. Прямого редактирования строк нет.
Ряды кнопок содержимого окна занимают всю ширину панели: кнопки делят её
поровну внутри каждого ряда, длинные надписи переносятся. Фиксированной ширины
кнопок нет; оконные значки используют штатные размеры.
Над кнопками остаётся только строка метаданных: слева метка
«путь к файлу со списком заданий:», затем `<имя базового каталога>/clark.tasks.txt`.
Это доступное браузеру представление пути, а не абсолютный путь Windows.
Постоянная инструкция с последовательностью нажатий и дублирующие сообщения
о состоянии связи удалены из окна списка. Связывание и его состояние показаны
в панели `TaskAccessDialog`, открываемой из `Tasks`. Сообщения текущих операций и
ошибок (`notice`/`error`) остаются под панелью кнопок.
Владелец файловых операций и URI — `src/services/taskLaunchService.js`.

Рабочий файл `clark.tasks.txt` расположен в корне выбранного базового каталога.
Он содержит относительные пути `проект/задание`; начальный `*` отключает строку.
Обновление обходит два уровня каталогов, включая legacy-задачи без `input3XX`,
сохраняет включение существующих строк, удаляет отсутствующие, новые отключает.
Изменения сразу записываются; запуск разрешён после завершения записи.
Выделение строк используется для изменения списка; запускаются все включённые строки.
Двойной щелчок по строке переключает `enabled` только этой записи, независимо
от множественного выделения. Кнопки «Подключить»/«Отключить» по-прежнему
действуют на выделенные строки. `TaskLaunchWindow.toggleEntry` вызывает
`setTaskListEntriesEnabled` через общий `changeList`: сохраняет список,
инвалидирует прежний запрос запуска и готовит новый после записи. Обработчик
сохраняет блокировки при записи, связывании и ожидании приёма запуска;
ошибка записи показывается без изменения состояния строк. Подсказка строки
называет действие следующего двойного щелчка.
Список и операции относятся к выбранному корню, независимо от загруженной BaseModel.
Перед запуском включённой редактируемой задачи пользователь сохраняет её изменения.
Импорт требует подтверждения замены исходных JSON и выгружает затронутую BaseModel.

Браузер не получает абсолютный путь каталога. С 4.68.0 кнопка связывания
использует [общий запрос для каталогов диска](#catalog-binding); локальная
программа регистрирует отдельный workspaceId для каждого базового каталога.
Перед доступностью команд редактор записывает свежий одноразовый запрос
`clark.launch.json`; совпадение запроса в зарегистрированном каталоге защищает
от запуска старого расположения после копирования дерева. URI открывается
непосредственно по щелчку; асинхронная подготовка завершена заранее.
Локальная программа поглощает запрос, пишет `clark.launch-result.json` и выполняет
фиксированную команду. До ответа `accepted` изменение списка и повторный запуск
закрыты: запускатель ещё может читать прежний одноразовый запрос и список.
После первого `accepted` метод `acceptRun` сохраняет наблюдаемый запрос,
но через `armLaunch` готовит новый `clark.launch.json`. `locked` учитывает
`busy`, ожидание приёма (`state=waiting`) и связывание, а не всё время расчёта.
`onBusyChange` передаёт родительскому `Tasks` только `busy || awaitingAcceptance()`. Пользователь может менять список и
повторять запуск без смены базового каталога; одновременный запуск нескольких
решателей предотвращает сам пользователь. Прежние условия `canLaunch`
(валидный непустой подключённый список, связь, сохранённая модель и готовый
запрос) остаются обязательными.

Повторные ответы `accepted` не пересоздают запрос и не стирают ошибки
операций списка. Закрытие PowerShell без финального ответа оставляет только
наблюдение за старым запросом, но не блокировку интерфейса. Новый запуск
заменяет наблюдаемый запрос; ответы прежнего запуска не меняют UI. После
чтения результата `pollNative` повторно проверяет `busy`/`bindingBusy`, чтобы
не завершать старый запуск одновременно с начавшейся записью списка.
`refreshOnFocus` может повторить подготовку запроса после ошибки записи,
даже если прежний расчёт остаётся в состоянии `accepted`.

Тайм-аут отсутствующего подтверждения (45 секунд), инвалидация старого proof
и повторное чтение результата перед снятием ожидания сохраняются. Если
`accepted` обнаружен при этой повторной проверке, используется тот же
`acceptRun`. Ошибки доступа и занятый файл не подменяются успешным запуском.
Результат перечитывается по идентификатору запроса; устаревшие ответы не меняют UI.
После завершения команды перечитываются сводки выбранной участвующей задачи;
после импорта также обновляется предварительный просмотр её геометрии.

Кнопка «Выбрать каталог с проектами» и её обработчик блокируются только
на время связывания каталога (`bindingBusy`), но не по `launchBusy`. Поэтому
смена корня доступна и во время выполнения, и при оставшемся `accepted` после
закрытия PowerShell без финального ответа. Отмена диалога ничего не меняет;
повторный выбор того же каталога сохраняет текущий корень и ожидание. Выбор
другого каталога запускает штатный сброс `TaskLaunchWindow`: старый `pending`
снимается, список перечитывается, ответы прежнего корня отсекаются через
`rootRevision` и проверку handle.

Уже запущенный локальный обработчик работает с отдельным снимком списка
заданий; смена каталога в браузере не перенаправляет и не останавливает
процессы. Смена корня прекращает наблюдение за прежним запросом и не
подтверждает завершение расчёта. Пользователь отвечает за запуск только одного
решателя одновременно; это явно указано в подсказке выбора каталога и README.
Глобальная блокировка процессов между каталогами не добавляется.

Формат URI и служебных файлов принадлежит
[solver/AI_RUN.md](https://github.com/y26084670-blip/solver/blob/main/docs/AI_RUN.md#run-web-gui).
OM-клиент сохраняет ограничение одной включённой REAL64-задачи. Решатель и
импорт работают со всеми включёнными заданиями. Для применения нужен установщик
с регистрацией протокола; постоянно работающий сервер не используется.

<a id="native-om-client"></a>
### Собранный OM-клиент

В `taskLaunchService.js` разрешено действие `modelica`, в `TaskLaunchWindow.jsx`
добавлена кнопка «Запустить OM-клиент». Используются тот же подтверждённый список,
workspace/request, ожидание accepted/completed/error и поле MPI. Для `modelica`,
как и для `circuit`, нужна ровно одна включённая задача. При ошибочном MPI кнопка
заблокирована. Прочие сценарии списка и импорта сохраняются.

Установленный `Invoke-ClarkProtocol.ps1` направляет запрос в `Invoke-ClarkOM.ps1`.
Тот выбирает готовый пакет по `input3XX/om-client.json`, читает модельные данные
и `server-config.json`, запускает OM с MPI Solver и учитывает оба завершения.
Компиляция не выполняется в пользовательском запуске. Требуются обновлённые GUI
и установленный обработчик; старый обработчик отклоняет неизвестное действие.
Подробный владелец: [solver/FMI](https://github.com/y26084670-blip/solver/blob/main/components/FMI/README.md).

Реальный браузерный запуск нового клиента на Windows ещё не подтверждён.
В 4.55.0 добавлен редактор JSON; его файловый контракт описан ниже,
[поведение окна](AI_UI_CONTRACTS.md#om-client-editor) — у владельца UI.

<a id="om-client-input-editor"></a>
### JSON задачи и пресет редактора OM — 4.56.0

Описание панели `contract.ui` необязательно и имеет схему `clark-om-panel/1`.
Оно содержит группы `groups` с `id`, `label`, необязательным `repeat` и полями
`fields`: `path`, `label`, необязательные `unit`, `description`, `type`, границы
и `options` (пары value/label). Пути повторяемых полей используют `$index`.
Типы и ограничения связанных параметров берутся из `parameterBindings`,
размерности — из `dimensions`, импульсы и масштабы — из `tables`;
дополнительные поля описывают тип явно. `ports` задаёт подписи каналов по
`side`/`kind`, с `{i}` в подписи и необязательной единицей. Код в описании запрещён.
Описание поставляет сборщик модели; JSON задания его не дублирует.
Старые пресеты без `ui` сохраняют режим JSON.

Форма и JSON редактируют один черновик; неизвестные свойства сохраняются.
При изменении размерностей координаты записей сохраняются по множителям
`arraySizes`, включая привязки. Новые привязки пусты до явного выбора.
Сокращение массивов требует подтверждения. Смена шаблона заменяет черновик
после подтверждения; выбор описания требует совпадения model и dataSchema,
версия сборки не является самостоятельной схемой интерфейса.

Каталог Clark принадлежит `omClarkBindings.js` и читает BaseModel: AMP —
индексы импульсов, PSI — уникальные indCoil с именами элементов/областей,
MOVE — записи движения (только первый угол), RSP — совместимый канал
сопротивления (текущий сервер возвращает ноль). Импульс ЭДС — отдельная ссылка
на таблицу задания, а не канал AMP. Неподдерживаемые типы не предлагаются;
отсутствующая ссылка сохраняется и получает ошибку. Несохранённые изменения
таблиц, от которых зависит привязка, блокируют OM-запись до сохранения поля.

`omClientService.js` читает три файла в `input3XX` загруженного для редактирования задания:
`om-client.json` (подключённая модель) либо `_om-client.json` (отключённая)
задаёт модель, версию, `dataFile` и `couplingFile`; два остальных
имени берутся именно из него. Для первой модели это `circuit-config.json` и
`server-config.json`. Файлы поля и `circuit-config.txt` этот сервис не меняет.
Данные OM не входят в BaseModel поля и сохраняются отдельной командой окна.

`setOMTaskEnabled` переключает только имя селектора: копирует исходный текст
без переформатирования, проверяет запись и неизменность снимков, затем удаляет
прежнее имя. Параметры, связи и импульсы при переключении не записываются.
При ошибке удаления копия откатывается, если она всё ещё принадлежит операции;
единственная полная копия не удаляется. Внешние изменения требуют перечитывания.
Это не атомарное переименование: при аварийном закрытии возможны оба селектора.
Их одновременное наличие блокирует чтение/изменение панели с явной ошибкой.
Сохранение отключённой модели пишет `_om-client.json` и не подключает её.
Нативный запуск по-прежнему требует активный `om-client.json`.
Файлы с прежним нештатным именем `om-client.json.disabled` автоматически не читаются;
для нового переключателя их следует переименовать в `_om-client.json`.
С 4.55.1 версия пакета не показана отдельным полем и не редактируется вручную:
она сохраняется из существующего `om-client.json` или приходит вместе с применённым
пресетом. Версия остаётся частью выбора установленного пакета; формат файлов не меняется.

Пресет `clark-om-preset/2` содержит `label`, `selection` (содержимое селектора),
`data`, `coupling` и `contract`. Последний получает из описания собранной модели
`dataSchema`, `structural`, `dimensions`, `arraySizes`, `parameterBindings`,
`tables`, `inputs`, `outputs`, необязательный `variants`. Варианты в пресете
содержат только условия выбора и минимальные размеры, без путей EXE/XML. Индексы обмена соответствуют порядку `variables` в группах. Допустимые
каналы текущего решателя: входы AMP/MOVE, выходы PSI/RSP. Пресет не содержит
исполняемого кода, путей запуска или команд. Его наличие не доказывает установку
модели; окончательную проверку пакета выполняет установленный запускатель.

`expandOMContract` проверяет целочисленные размерности и разворачивает контракт
на действующие элементы. Размер массива задаётся числом или произведением имён
размерностей (`phases*parallel`). Записи `repeat` используют индекс `{i}` с 1
в именах переменных и `$index` с 0 в путях JSON. Предел — 10000 элементов массива.
Действующие ветви идут подряд, резервные записи в JSON не допускаются.
`floatingNeutral` должен быть Boolean; ровно один вариант должен удовлетворять
условиям `when`. Изолированная цепь требует минимум две действующие ветви.
Встроенные образцы не фиксируют вместимость неизвестного локального пакета.
Импорт его `editor-preset.json` добавляет точные максимумы для проверки в GUI;
окончательную проверку выполняет запускатель до старта процессов. Общая схема
данных цепи `clark-circuit/2` не меняется; обратного преобразования пресетов нет.

В `src/data/om-presets` файлы `circuit-single.json` и `circuit-star.json`
используют только `clark-circuit/2`, версию пакета 2.0.0 и ссылки на импульсы
задания. Это шаблоны однофазной цепи и трёхфазной изолированной звезды,
а не автоматически готовые данные задания: номера импульсов должны существовать
и соответствовать пользовательской постановке. Старые `/1`-пресеты исключены.
Частный пресет 204 удалён: существующие учебные задания читаются по общему
контракту цепи с сохранением собственных параметров.
При открытии существующей задачи её файлы имеют приоритет и автоматически
пресетом не заменяются. Импорт `editor-preset.json` из пакета модели добавляет
новый вариант в выпадающий список без изменения JS. Импортированные пресеты
хранятся в localStorage этого origin; при отказе хранилища работают до закрытия
страницы с явным сообщением. Смена домена/браузера требует повторного импорта.
Неподдерживаемая модель отображается, но для проверки/сохранения нужен её пресет.

Проверяются JSON без повторных ключей и неограниченных чисел, модель и схема,
структурные скаляры, размеры массивов, типы и границы runtime-параметров,
положительные допуски, таблицы времени с минимум двумя строго возрастающими
точками, группы и число положительных индексов каналов. Проверка не устанавливает
физическую корректность постановки. Для `task-pulse` проверяются положительный
целый Int32-номер, конечный коэффициент, существование импульса и его конечные,
строго возрастающие точки; проверяется также конечность масштабированных значений.
Окно передаёт текущую readonly `BaseModel.amps`, но при dirty импульсов требует
сначала общее сохранение поля. Файловый сервис перед OM-записью отдельно читает
`amplitudes.txt` и сравнивает его текст в ходе записи. Весь банк, включая
неиспользуемые OM записи, должен содержать корректные импульсы: `n >= 2`
в пределах Int32, ровно `2*n` конечных значений, строго возрастающее время.
Пустые строки-записи не разрешены; одно завершающее переведение строки допустимо.
Индексы каналов обмена по несохранённой BaseModel поля не проверяются. Данные поля надо сохранить отдельно; установленный клиент остаётся владельцем
предпусковой проверки. Предельный размер одного JSON — 4 МиБ. Неизвестные свойства
не удаляются при сохранении; имена файлов — отдельные безопасные имена JSON.

Запись начинается после проверки всех данных и сравнения исходных файлов со
снимками чтения. Внешняя правка требует перечитывания. Сначала пишутся данные и
обмен, последним — селектор. Ошибка записи вызывает попытку восстановления только
собственных записей; сторонняя правка не затирается. Невосстановленные файлы
перечисляются в ошибке. Это не атомарная транзакция трёх файлов: аварийное закрытие
браузера во время записи требует проверки комплекта. Старые файлы при выборе
модели с другими именами не удаляются. Во время записи и при несохранённом OM-черновике
окно запуска блокирует команды с пояснением. Подтверждённый расчёт не запускается
автоматически после сохранения.

<a id="om-pulse-inputs"></a>
### Временные зависимости через импульсы задания — 4.56.0

`clark-circuit/2` заменяет `emf[k].points` на
`emf[k] = {"pulse": N, "amplitude": A}`. `N` — 1-based запись
`input3XX/amplitudes.txt`; `A` — коэффициент ЭДС в В.
`E_k(t) = A_k * f_N(t)`, без автоматической нормировки. Таблица хранит время
в секундах и значения формы; в новом формате нет общего поля `amplitude`.
Между точками — линейная интерполяция, вне таблицы — удержание крайнего
значения. Действующее правило Circuit для `t <= 0` (нулевая ЭДС) сохранено.
Отрицательный и нулевой коэффициенты допустимы. Повторное использование
одного импульса в разных временных зависимостях допустимо.

Контракт пресета/пакета описывает этот источник универсально:

```json
{"name":"emf1","source":"task-pulse",
 "pulsePath":["emf",0,"pulse"],"scalePath":["emf",0,"amplitude"]}
```

У будущей модели пути и физическая размерность коэффициента принадлежат её
описанию; интеграционный механизм не ограничен ключом `emf`.
Для временной зависимости разрешён только `source: "task-pulse"`.
Цепь использует только `clark-circuit/2`. Селектор `clark-om-client/1`, обмен
`clark-server/1` и контейнер пресета `clark-om-preset/2` имеют самостоятельные
версии: они не обозначают схему цепи.
Нужен пакет с поддержкой `task-pulse`; встроенные пресеты указывают circuit/2.0.0.
Загрузка пресета не устанавливает пакет. Изменение номера/формы/коэффициента
не требует сборки. Число фаз/ветвей меняется в пределах вместимости пакета,
тип нейтрали выбирает готовый вариант автоматически.

OM runtime в `solver/components/FMI/ClarkOM.psm1` разрешает ссылки перед
запуском из сохранённого файла и создаёт рабочие таблицы пакета. Штатный запуск
не требует Python или компилятора. Сборка цепи не читает задание: `-MaxPhases` и `-MaxParallel` задают максимумы,
`-Version` — версию (по умолчанию 2.0.0). Оба варианта нейтрали входят в один пакет.
Из корня solver выполняются CMD `build/configure_om_client.cmd`,
`build/build_om_client.cmd`, `build/install_om_client.cmd`. Локальный
`components/FMI/om-build-settings.json` содержит только пути инструментов
сборки; установка готового пакета и расчёт его не читают.
Полный контракт пакета и проверок —
[solver/OM](https://github.com/y26084670-blip/solver/blob/main/components/FMI/README.md).

## Число процессов MPI и получение настроек (4.25.0)

В `TaskLaunchWindow` поле «Процессов MPI» содержит число, прочитанное локальным
запускателем из установленного runtime.json, либо буквальное `default`.
При привязке значение приходит в `clark.workspace.json`; при открытии окна
`Tasks.openTaskLaunch` непосредственно по щелчку вызывает отдельный запрос
настроек через `clark://settings`. Поддержка определяется полем
`launchOptionsVersion: 1` bound-маркера; старому обработчику запрос не отправляется.
Браузер может запросить штатное разрешение на открытие внешнего приложения.

До свежего ответа поле без ручной правки показывает default. Ответ читается
из `clark.settings.json` и принимается только для текущего каталога и requestId.
Отсутствующий/занятый файл повторно читается до 45 секунд; поздний ответ другого
запроса не меняет поле. Ручное значение не перезаписывается асинхронным ответом.
Смена корня сбрасывает ручной выбор и ожидание настроек.

Автоматически показанное число информационное: пока поле не редактировали,
при запуске используется актуальный runtime.json. Ручное положительное целое
1…2147483647 передаётся как необязательный mpiRanks в URI solver/circuit/modelica.
Пустой ввод нормализуется в default при потере фокуса; default снимает
переопределение. Дробные, нулевые и отрицательные значения блокируют кнопки
расчёта, но не импорт. При старом обработчике ручное переопределение явно
требует обновить Clark и повторить привязку, без запуска с неправильным числом.

Настройка относится ко всем включённым заданиям данного запуска и MPI-серверу
цепи; клиент цепи не становится MPI-программой. GUI не меняет runtime.json,
BaseModel или исходные данные заданий. Точный нативный контракт и поведение
диалога принадлежат [solver/AI_RUN.md](https://github.com/y26084670-blip/solver/blob/main/docs/AI_RUN.md#run-web-gui).

<a id="task-summaries"></a>
## Сводки исходных данных и результатов (4.24.0)

`web-gui` владеет `input3XX/_summary.txt`. `taskSummaryService.formatTaskSummary`
формирует UTF-8-текст из фиксированного снимка BaseModel, переданного из
`App.handleSave`; `writeTaskSummary` заменяет файл после записи исходных данных,
до подтверждающей проверки. Поток закрывается после полной записи, при ошибке
выполняется `abort`; ошибка не маскируется успешным сохранением.
[Порядок и маркер](AI_DATA_CONTRACTS.md#маркер-подтверждения-исходных-данных).

Сводка содержит дату сохранения ISO 8601 UTC, выбранную разрядность, число
обычных элементов (`targ=0/1/2`, без виртуальных), областей, измерительных
катушек, импульсов и траекторий. Число катушек — максимальный абсолютный
`indCoil` виртуальных элементов и областей, по семантике `solver/01_counters.jl`.
Для ВТСП указываются подключённые подсистемы и FC/ZFC; при включении —
расчёт сил/моментов. Ненулевые PPJ/PPM вычисляются через общие `kvFlags` и
`eoCount`, включая независимые образы симметрии и заданные источники.
Последние строки — шаг времени и число интервалов без добавления начального
состояния. Неизвестные дата запуска и длительность расчёта не подставляются.

`solver` больше не создаёт и не дополняет `_summary.txt`. Он удаляет старый
`output3XX/_summary_out.txt` при инициализации расчёта и публикует новый только
после штатного завершения. Это около 30 строк: даты, режим/разрядность/MPI,
счётчики, временной диапазон, накопленные тайминги и фактически записанные
HDF5-результаты. Подробный контракт принадлежит
[solver/AI_RUN.md](https://github.com/y26084670-blip/solver/blob/main/docs/AI_RUN.md#run-protocols).
Редактор читает результат как обычный текст, без вычислений и подмены содержимого.
Старые установленные сборки solver сохраняют прежнее поведение до обновления.

## Необязательные зависимости времени и indAmp

Legacy-импортёр solver допускает отсутствие `MHJamp.in` и `MOVIEW.in` и
формирует пустые списки импульсов/траекторий. Ссылки объектов не исправляются:
[полный контракт импортёра](https://github.com/y26084670-blip/solver/blob/main/docs/AI_IMPORT.md).
Редактор проверяет ссылки по текущим `amps`/`moves`, включая несохранённые
записи: [контракт диагностики](AI_DATA_CONTRACTS.md#time-references).

Для `targ=3` допустим целый `indAmp` 0…3: ноль задаёт поле в центрах,
1–3 — направления D1–D3. Отрицательные значения недопустимы.
Этот код не является ссылкой на импульс и не требует `amplitudes.txt`.

## Подготовка геометрии и действующий решатель, 22.09.2026

Практические правила ШГ, укрупнения, MED и контрольных центров принадлежат
[AI_GEOMETRY_GENERATION.md](AI_GEOMETRY_GENERATION.md). Эта тема применяется
в рабочих моделях, её каноническое место не зависит от текущего теста.

Текущий solver использует полный Newton J/λ: сильный материальный E(J,H,M),
аналитическая касательная, GMRES полного связанного оператора и разреженный
предобусловливатель. MAG-согласование остаётся внешним; это не полный Newton J/M.
Исторические KB1/KEPS1 локального поиска не определяют действующий глобальный
алгоритм. Формулы и критерии — [численный контракт solver](https://github.com/y26084670-blip/solver/blob/main/docs/AI_NUMERICAL_CONTRACTS.md#nc-jweak-nonlinear).

Дополнительный `input3XX/jweak_local.json` описывает локальное иерархическое
пространство solver. В 4.27.0 добавлена ограниченная поддержка готового файла:
редактор проверяет допустимость иерархии и родительские стыки, не меняя фактические
`dp`, MED и байты дополнения. Состав и порядок KV зафиксированы; полноценного
редактора родителей и структурного преобразования иерархии нет.
[Канонический контракт загрузки, проверки и сохранения](AI_DATA_CONTRACTS.md#jweak-local-input),
[интерфейс](AI_UI_CONTRACTS.md#jweak-local-ui),
[математический контракт solver](https://github.com/y26084670-blip/solver/blob/main/docs/AI_NUMERICAL_CONTRACTS.md#nc-jweak-local).
Обычный и полный Newton не определяют этот режим; алгоритмы solver, формат файла
и исходные данные теста данной правкой не изменены.

reference/comparison.json — метаданные внешнего сопоставления в clark.tests,
не вход уравнений solver. Координаты определяют физическую контрольную точку;
номер ЭО нужен только для выборки из конкретного результата и проверяется по
координатам. Изменение имени папки задачи не меняет физического эталона;
ссылки/списки задач при переименовании должны указывать на новый путь.


<a id="task-directory-operations"></a>
## Создание, копирование, переименование и перенос заданий (4.29.0)

Владелец файловых операций — `taskDirectoryService.js`, JSX не копирует файлы.
`taskTemplateService.js` создаёт черновик через `tabRegistry`, defaults схем и
`dataService.save`: общие параметры, две записи conrab, пустые kvs/tks/amps/moves,
одна MHJ-запись с пустым `v`. С 4.30.1 шаблон нового задания явно задаёт
`general.htsMu=false` и `general.htsRo=false`: обе подсистемы ВТСП отключены.
Это настройка `taskTemplateService`, а не изменение defaults десериализации:
чтение существующих файлов и копирование сохраняют их значения.
Записывается `_summary.txt`; `_nogo.e3d` остаётся
до штатной проверки и сохранения. Геометрия и материалы не придумываются.

Создание/копия выполняются в выбранном проекте. Копия требует `input3XX`, берёт
сохранённое дерево и дополнительные входы, включая локальные xapLibFMM/HTS,
`jweak_local.json`, формулы, произвольные бинарные входы. Исключаются каталоги
`output3XX`, `logs`, `tmp`, `temp`, `.git`, файлы `*.log`, `*.tmp`, `*.temp`,
с завершающим `~`, `_summary_out.txt` и старый `_nogo.e3d` (регистр неважен).
Новый маркер проверки создаётся независимо от статуса оригинала. MED и dp
не пересчитываются. Неизвестные файлы вне исключений сохраняются.

Переименование и перенос копируют **всё дерево**, включая результаты, пустые
каталоги, старый маркер проверки и дополнения. Применяется переносимый механизм
copy → verify → update references → delete, а не неподдерживаемый `handle.move`.
Назначение должно быть проектом: внутри известного root — ровно один уровень;
корень, вложенное задание и потомки источника запрещены. Вне root принимается
выбранный каталог проекта; его чужой `clark.tasks.txt` не изменяется.

Имена: до 120 символов, без путей, управляющих/служебных символов Windows,
зарезервированных имён и точек/пробелов в конце. Конфликты учитывают NFC и
регистр; переименование только регистра также отклоняется. Перезапись отсутствует.
Перед созданием имя проверяется повторно после чтения источника.

Для каждого файла строится манифест `путь, тип, размер, SHA-256`; файлы читаются
последовательно, память на хеширование — до размера одного файла. После копии
снова читаются назначение и источник; при перемещении источник повторно
проверяется перед удалением. Несовпадение, новый/удалённый файл и замена
дескриптора источника блокируют удаление. Копирование/хеширование асинхронные,
без Worker, с настоящими File/stream операциями браузера.

В неполном назначении современного формата выставляется `_nogo.e3d`.
При успешном перемещении восстанавливается прежнее состояние маркера;
при legacy-переносе новый `input3XX` не создаётся. Ошибочная legacy-копия может
содержать неполный комплект; сообщение запрещает считать её завершённой.
При ошибке назначения автоматически не удаляются. `operationResult` возвращает
handle, verified, deletionStarted и sourceRemoved для восстановления UI.
После начала удаления оно может быть частичным; в этом случае проверенная
копия назначения сохраняется и становится адресом ранее загруженного задания.

Если `clark.tasks.txt` существует, он читается до операции и повторно сравнивается
перед записью. Новая задача/копия добавляется отключённой. Переименование/перенос
внутри root сохраняет enabled исходной строки; внешнее перемещение удаляет
исходную строку. Несуществующий список не создаётся. Устаревшая строка назначения
или неверный формат блокируют операцию. Штатный `writeTaskList` инвалидирует
старый `clark.launch.json`. При сбое записи списка источник не удаляется;
возможно наличие проверенного назначения и частично обновлённого списка —
пользователь получает ошибку и должен проверить оба каталога и список.

File System Access не предоставляет транзакцию дерева, эксклюзивный mkdir,
межпроцессную блокировку или атомарный compare-and-swap списка. Поэтому механизм
не гарантирует безопасность при продолжающейся внешней записи после последней
проверки. Подтверждение остановки писателей в диалоге — необходимое условие.
Другие внешние ярлыки, списки и уже запущенный Clark не перенаправляются GUI.
Перенос требует места для полной второй копии до удаления источника.

<a id="task-directory-delete"></a>
## Удаление задания (4.30.0)

`runTaskDirectoryOperation({kind: "delete", root, sourceParent, source})`
делегирует удаление отдельной ветви `deleteTaskDirectory` без копирования,
хеширования и чтения содержимого задания. Дескриптор источника должен быть
непосредственным ребёнком проекта, а проект — ребёнком выбранного root.
Корень, сам проект, вложенные каталоги и чужие задания отклоняются. Проверка
`isSameEntry` повторяется перед изменением списка и перед `removeEntry`.

До удаления читается существующий `clark.tasks.txt`, проверяется отсутствие
его изменения и штатным `writeTaskList` исключается только строка источника.
Остальные пути и enabled сохраняются. Подготовленный `clark.launch.json`
инвалидируется, в том числе если списка нет; отсутствующий список не создаётся.
Ошибка чтения/записи или инвалидирования блокирует удаление дерева.

После этого `sourceParent.removeEntry(source.name, {recursive: true})`
удаляет все файлы и подкаталоги, включая результаты. Нет корзины, резервной
копии или модельного Undo. Операция не транзакционная: при отказе удаления
часть файлов может уже отсутствовать, а строка запуска уже исключена.
`operationResult` содержит `deletionStarted` и `sourceRemoved`; UI обновляет
список даже при частичном удалении и закрывает затронутое открытое задание.
При ошибке повторная отправка из того же диалога блокируется. Пользователь
проверяет оставшийся каталог перед новой операцией. Внешние ссылки и уже
запущенные процессы не управляются; подтверждение остановки писателей
использует существующий механизм диалога файловых операций.

<a id="task-import-used-fmm"></a>
## Автоперенос используемых ФММ после импорта заданий (4.33.0)

После `completed` для запроса `action=import` панель передаёт в `Tasks` снимок
списка запуска, исходный root handle и проверку актуальности контекста.
До обновления предпросмотра `taskImportMaterialsService` последовательно
обрабатывает все включённые задания, независимо от выделения и загруженной модели.

Если в корне задания имеется `XAP.lib` (регистр имени файла несущественен), сервис
читает свежий `input3XX/kvs.txt` как JSON Lines и собирает непустые имена `xapName`
для `model` 0/1. Повторы исключаются по trim/NFC/регистронезависимому ключу,
как при проверке ссылок редактора. Сохраняется первое написание имени.
Назначение, take, видимость и выделение не ограничивают список; model=2 (ВТСП)
не участвует в импорте ФММ. Пустой список не создаёт библиотеку.

Штатный `parseXapLibrary` проверяет библиотеку; выбираются только записи из
составленного списка. `createFmmMaterialFile` сохраняет штатный column-major JSON.
Отсутствующие имена дают только информационные сообщения с путём задания,
не мешают записи найденных характеристик и переходу к следующему заданию.
Если отсутствуют все имена, файловая запись не выполняется. Исходные ссылки
не обнуляются; последующая обычная диагностика модели по-прежнему их проверяет.

`taskMaterialLibraryService.writeImportedBatch` выполняет запись в
`input3XX/xapLibFMM`. Одноимённые отличающиеся файлы заменяются по подтверждённой
команде импорта; пакет сначала проходит штатный preflight, затем повторно
проверяются SHA конфликтов. Побайтово одинаковые файлы не переписываются.
Посторонние локальные характеристики не удаляются. Повреждение библиотеки,
неоднозначность имён, некорректный JSON или файловая ошибка отображаются как
ошибка соответствующего задания; последующие задания обрабатываются дальше.
Ошибка записи может оставить частичный пакет — это не транзакционная ФС.
После попытки записи публикуется штатная ревизия библиотеки ФММ.

Для этого автоматического сценария запрет ручного импорта стандартной XAP.lib
по SHA-256 не применяется: локальная библиотека служит источником независимо
от совпадения с базовой. Тот же механизм используется кнопкой локальной библиотеки ФММ.
Нет XAP.lib — прежнее поведение без дополнительных записей.

При native-ошибке всего списка автоперенос не выполняется: протокол не сообщает,
какие конкретно задания успешно обновлены, и старый kvs.txt нельзя считать свежим.
Это отдельно объясняется в информационном отчёте; исходная native-ошибка сохраняется.
Обработанные/пропущенные имена видны в раскрываемом отчёте панели; отсутствие
имени не превращает успешно завершённый native-импорт в ошибку запуска.

Пока идёт браузерный этап, панель занята. Страница должна оставаться открытой,
базовый каталог и наблюдаемый запуск должны сохраняться до завершения.
Смена корня прекращает начало следующих операций и отбрасывает старый отчёт;
уже начатый пакет может закончить запись только в захваченный прежний каталог.
Новый root никогда не подставляется в старый запуск. Маркер `_nogo.e3d` не снимается.
Сохранение, проверка и дальнейший расчёт остаются штатными отдельными действиями.
Solver, его установленный импортёр и формат clark:// не изменены.

### Импорт из вкладки ФММ (4.33.1)

`MaterialLibraryTab` передаёт `modelService.getModel().elements` в общий
`importUsedFmmMaterials(taskHandle, elements, options)`. Список уникальных
имён фиксируется синхронно до первого await: используются несохранённые
элементы, все строки без фильтра/выделения. `kvs.txt` здесь не читается.
Сервис выбирает локальную XAP.lib без учёта регистра, проверяет пакет и
заменяет только найденные используемые ФММ штатным writer с SHA preflight.
Повтор без изменений не переписывает файлы. Недостающие имена — info.
Стандартная XAP.lib допускается. Файлы других характеристик сохраняются.
Вызов из списка по-прежнему использует свежий kvs.txt после native completed.

Кнопка блокирована при несохранённых правках самой библиотеки. Импорт не
сохраняет BaseModel; запись библиотеки непосредственная, её Undo/Redo
сбрасывается. Ревизия ФММ обновляет таблицу; прежняя ручная диагностика
сбрасывается как устаревшая. Повторная команда «Проверить модель» читает
обновлённую локальную библиотеку.
При смене задания/источника или размонтировании проверка `isCurrent`
останавливает последующие записи и публикацию отчёта. Уже начатый пакет
может завершиться только в захваченном старом каталоге.
Ошибки чтения/записи показываются как ошибки; отсутствие имён не блокирует
найденные записи. Проверки занятости целевых имён и целостности текущей операции сохранены; внешняя правка с момента открытия больше не блокирует явное сохранение.

<a id="constant-mu-file"></a>
## Файл сгенерированной характеристики μ=const — 4.45.0

`src/services/materials/constantMuFmm.js` использует штатный
`createFmmMaterialFile` и `taskMaterialLibraryService.writeImportedBatch`.
Формат не расширяется: UTF-8 JSON с расширением `.txt`; `tabl` содержит сначала
12 значений H (кА/м), затем 12 значений M (кА/м), `hip=μ−1`, `comment` описывает
параметры генерации. Последняя точка H=Hmax; между точками исходная линейная
зависимость M=(μ−1)H сохраняется, `hip` задаёт ту же производную продолжения.
μ=1 создаёт 12 нулевых M; 0<μ<1 не запрещено генератором. Неконечные числа,
неположительные параметры, переполнение M и неразличимые узлы H отклоняются
до записи. Допустимость выбранной характеристики для конкретной физической
постановки оценивается отдельно.

Имя определяется исходным μ, округлённым только для названия до двух знаков:
μ=1234 → `1234.00.txt`; математические значения от этого округления не меняются.
Поэтому разные μ с одинаковым округлённым именем записываются в один файл,
который явная команда «Сохранить» заменяет. Каталог — локальный
`input3XX/xapLibFMM`; встроенные ресурсы приложения не изменяются. При конфликте
имени повторный preflight передаёт наблюдаемые `expectedConflicts`/SHA и
`overwrite=true`. Внешнее изменение между проверками завершает операцию ошибкой,
а не безусловной повторной перезаписью.

<a id="installer-download"></a>
## Прямая загрузка установщика

`installerDownloadService.js` формирует `clark://download-installer?request=<GUID>`.
Другие параметры, URL файла и пути не передаются. Каталог задач и workspace не нужны.
Обработчик solver `Invoke-ClarkProtocol.ps1` вызывает `Download-ClarkInstaller.ps1`.
Он читает фиксированный `https://y26084670-blip.github.io/clark-editor/examples-config.json`,
проверяет HTTPS и скачивает файл. Фиксированные размер и SHA-256 не используются.
Прямой HTTPS URL используется сразу; публичная ссылка Mail.ru разрешается локально
через `weblink_get` в странице. Это внутренний формат сервиса, при его изменении
потребуется обновить обработчик. Прокси-сервера нет.

Выбор пути, прогресс, проверка и предложение запуска принадлежат локальному обработчику.
До завершения загрузки и проверки MZ-заголовка прежний файл не заменяется.
При наличии Content-Length загрузчик проверяет полноту ответа, без ручных метаданных.
Метка интернет-зоны Windows сохраняется. Отмена или отсутствие обработчика не
определяются браузером надёжно: пользователь может снять отметку и использовать
обычную ссылку. Старый обработчик не поддерживает команду; для первого применения
нужно один раз установить обновлённую поставку обычным способом.
Полный контракт загрузчика — [solver AI_RUN](https://github.com/y26084670-blip/solver/blob/main/docs/AI_RUN.md#run-installer-download).

## Явный выбор задания между приложениями — Editor 4.74.0 / Viewer 4.49.1

`taskSelectionChannel.js` и его Node-тест одинаковы в обоих приложениях.
Команда `select-task` канала `clark.task-selection.v1` содержит baseHandle,
дополнительный diskHandle, projectName и taskName. Протокол сохраняет version=1;
старый получатель игнорирует diskHandle и может требовать прежнего совпадения
каталогов. Для полного исправления обновляются оба приложения.

Сначала получатель ищет точный baseHandle через isSameEntry среди текущего
каталога и своей копии списка. При отсутствии обновляет непосредственные clark.*
каталоги своего диска, затем диска из явной команды. Перед перечислением
проверяется уже предоставленное разрешение read. Совпадения имён недостаточно;
искомый каталог должен действительно принадлежать доступному диску. clark.app
и вложенные каталоги не используются как подмена. Ни requestPermission, ни
файловые записи, ни изменение общей IndexedDB здесь не выполняются.

После успешного чтения всех уровней получатель согласованно меняет свои диск,
список каталогов, каталог, проект и выделенное задание. Загруженная модель Editor
и результаты Viewer сохраняются. Поздний ответ после смены состояния отменяется.
Ошибка сообщает причину отправителю; автоматического открытия вкладки нет.
Пассивное уведомление о сохранённом диске по-прежнему не переключает другой GUI;
перенос выбора относится только к явной команде пользователя.
